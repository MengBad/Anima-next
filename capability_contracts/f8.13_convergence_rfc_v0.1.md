# F8.13 Convergence RFC — Capability Governance Convergence Boundary

> RFC（正文）。本文件定义 F8 系列治理能力（Resolution / Health / Recovery 三条链）的**收敛边界契约与裁定**。
> 派生自只读勘察 ADR `f8.13_convergence_scope_freeze_v0.1.md`（其结论已成立，可进入正文）。
> **核心裁定：Convergence = 仅文档级收敛（documentation-level convergence），不需要任何新抽象、不需要实现。**
> 本文件只冻结边界与共存契约，不实现、不改任何代码。与同系列文档一致，以 untracked 文档交付（经用户授权的 F8.13 文档收口 commit 纳入）。

## 1. Problem Statement

F8.1 → F8.12 已闭环三层治理能力：

```
Resolution 链 : resolve() → ResolutionEvent  ──► (F8.7 AuditStore, opt-in)
Health 链     : governed execution → NormalizedExecutionOutcome(F8.11) → HealthEvidence ──► HealthEvidenceStore
Recovery 链   : HealthEvidence → HealthPolicyEvaluator → RecoveryDecision → HealthObserver → TransitionStore
```

随着 Recovery（F8.12）落地，治理能力面趋于完整，但出现一个收敛问题：**三层治理能力是否职责重复、能否长期共存、哪些接口应进入稳定期、哪些能力应继续冻结**。若不显式裁定收敛边界，后续 slice 可能：

- 误把三条链中某条的事实"合并"进另一条，破坏各自 append-only 的审计语义；
- 把 `RecoveryDecision` 误开第四个独立 store，造成与 `TransitionStore` 的重复存储；
- 在 `CapabilityContract` 上继续加字段，侵蚀 RFC-0001A 已冻结的 contract 边界；
- 引入新的 Convergence runtime layer，违反"治理是旁路 RECORD/observer"的迁移边界。

本 RFC **不是新功能**，而是一次收敛盘点 + 边界冻结。它回答用户在 F8.13 授权中提出的五个问题（Q1–Q5），并据此裁定：三条链按设计正交共存，**Convergence 的全部工作 = 冻结边界 + 文档化共存契约**，无需新代码。

## 2. Current Facts (file:line)

### 2.1 三条链的事实载体

| 链 | 事实载体 | 记录时机 | 关键字段 | 持久化 |
|-|-|-|-|-|
| Resolution (F8.3) | `ResolutionEvent`（`governance/audit.py:96-113`） | `resolve()` 选择时 | `execution_key` / `candidates` / `selected_provider` / `outcome` | 经 `AuditSink` 旁路；默认 `InMemoryAuditSink`（不落盘），F8.7 持久 sink 可选 |
| Health (F8.10/11) | `HealthEvidence`（`health/model.py:21-49`） | 执行观测后 | `selected` / `executed` / `success` 分离 | `HealthEvidenceStore`（append-only，落盘） |
| Recovery/Lifecycle (F8.8/12) | `LifecycleTransition`（`ops/transition_store.py`）+ `RecoveryDecision`（`ops/decision.py`） | 治理状态变更时 | `source`/`target`/`reason`/`at` | `TransitionStore`（JSONL append-only，落盘） |

- `ResolutionEvent` 与 `HealthEvidence` 经 `execution_key` 对齐**同一次**执行（`audit.py:100-102`），但记录的是**不同决策时刻**的事实（选择 vs 执行观测）。
- `RecoveryDecision` **不落独立库**：经 `as_transition_reason()` 序列化为 `transition_to(reason=...)`，随 transition 进 `TransitionStore`（`decision.py:8-20`）。回溯一条 transition 即可同时见「变成什么 + 基于哪段窗口」。

### 2.2 决策 / 执行 / 记录三者边界

- `HealthPolicyEvaluator`（`ops/health_policy_evaluator.py`）：**纯函数**，读 evidence 窗口 → 产出 `RecoveryDecision`。不持 lifecycle 引用、不改任何状态、无 timer/daemon/polling（R1/R2/R3，`health_policy_evaluator.py:42-48`）。
- `HealthObserver`（`ops/observer.py`）：**执行者非决策者**，ops 包内唯一 `transition_to()` 调用点；`recover()` 仅收 `QUARANTINED→ACTIVE`（`:87-123`），`report_unhealthy()` 推 `→QUARANTINED`；fail-open（store 失败 ≠ 治理失败）。
- `audit`（`governance/audit.py`）：选择时记录，经 `AuditSink` 注入，fail-open（`resolver.py:515-529`）。
- `lifecycle.py` **不 import runtime**，是纯状态机 + 纯记录（`:39-42`）；`transition_to` 唯一写入点（`:125, :193`）。

### 2.3 两个 contract

- `CapabilityContract`（`runtime/capability_resolver.py:148-162`）：`capability_id / permission / side_effect / idempotent / timeout / retry`——**RFC-0001A 冻结元数据**，明确「Frozen」。
- `HealthPolicy`（`ops/policy.py:78-127`）：recovery policy schema（`failure_window / minimum_samples / failure_threshold / unknown_handling / unknown_dilution_k / recovery_condition`）。**出厂为空**是裁定不是遗漏（`:11-18`）——无生产流量支撑阈值取值，猜错阈值比没有策略更糟。

### 2.4 迁移边界（seam-based）

- runtime 经 `CapabilityRegistry.lifecycle_for()` 只读访问 governance（`capability_resolver.py:263-269`）；`resolve()` **不读 lifecycle**（QUARANTINED capability 仍可解析，fallback 语义保留，`:41-44`）。
- `audit_sink` 注入 resolver（opt-in, fail-open，`:374-382, :515-529`）。
- `HealthEvidence` 在受治理执行观测点经 route + sink 注入发射（F8.10.1）。

## 3. Architecture Questions（F8.13 裁定）

### Q1 — ResolutionEvent / HealthEvidence / TransitionStore 是否职责稳定、是否存在重复存储语义

**裁定：三者职责稳定、正交，无重复存储语义。共存为三个 append-only store，冻结各自 schema，不合并。**

- **不同决策时刻**：ResolutionEvent = 选择时（"用了哪个 provider、为什么"）；HealthEvidence = 执行观测后（"发生了什么"）；TransitionStore = 治理状态变更时（"处于什么状态、为什么"）。
- **无字段级重复**：
  - `ResolutionEvent.selected_provider`（选择结果）vs `HealthEvidence.selected`（resolution 是否选中 provider）——前者是"选了谁"，后者是"resolution 层是否选中"，语义不同；
  - `ResolutionEvent.outcome`（SELECTED / UNAVAILABLE 等**选择结局**）vs `HealthEvidence.success`（**执行成败**，来自 observation）——两个不同事实，不在同一时刻产生；
  - 三者仅共享关联键（`execution_key` / `capability_id`）用于交叉回溯，不重复存同一事实。
- **ResolutionEvent 默认不落盘是刻意边界（非缺口）**：审计是旁路，默认 `InMemoryAuditSink`（`audit.py:127-148`）避免长跑涨内存；耐久由 F8.7 持久 sink 按需接入。Convergence 不强制其耐久化。

→ 进入稳定期：`ResolutionEvent` schema、`HealthEvidence` schema、`TransitionStore` envelope schema（均冻结）。

### Q2 — RecoveryDecision 应长期保留，还是属于 Lifecycle command projection

**裁定：属于 Lifecycle command projection，不长期保留为独立 store。冻结此设计。**

- `decision.py:8-22` 已论证：系统已有三个 append-only store 各记一种事实，`RecoveryDecision` 属第三类——它**就是**那条 lifecycle decision 的理由。经 `as_transition_reason()` 随 transition 落 `TransitionStore`，回溯一条 transition 即可同时见「变成什么 + 基于哪段窗口/统计」。
- 单开第四个 store 的前提是「按 decision 查询/聚合」需求——目前不存在。
- 生命周期：进程内内存对象，evaluator 产出、observer 消费，不持久化、不缓存、不复用（`decision.py:24-26`）。

→ 冻结：`RecoveryDecision` 不落独立 store；`as_transition_reason()` 为稳定审计出口。

### Q3 — evaluator / observer / audit 三者边界是否需要进一步冻结

**裁定：边界已由设计冻结，无需进一步冻结。文档化为稳定边界契约。**

- 单向链：`HealthEvidence → Evaluator(决策) → Observer(执行) → TransitionStore`；`audit` 在 `resolve()` 选择时旁路记录。
- 守卫已就位：
  - evaluator：R1 不 import runtime/lifecycle、R2 只读 evidence 不回写、R3 无 timer/daemon/polling（`health_policy_evaluator.py:42-48`）；
  - observer：ops 包内唯一 `transition_to()` 调用点，`recover()` 守卫 `QUARANTINED→ACTIVE` 单向（`observer.py:87-123`），fail-open；
  - audit：`AuditSink` 注入 + fail-open，不阻断执行（`resolver.py:515-529`）；
  - lifecycle：纯状态机，不 import runtime，唯一写入点有源码扫描测试守门（`lifecycle.py:39-42, :193`）。
- 三角色**永不合并**：evaluator 决策、observer 执行、audit 记录选择。

→ 冻结边界契约："evaluator 决策、observer 执行、audit 记录选择 —— 三者职责不交叉"。

### Q4 — capability contract 是否已达稳定版本，哪些字段禁止继续增长

**裁定：两个 contract 均稳定。CapabilityContract 字段集 HARD FREEZE；HealthPolicy schema 冻结、取值为运营配置（不在代码内钉）。**

- `CapabilityContract`（RFC-0001A）：字段集 `capability_id / permission / side_effect / idempotent / timeout / retry`，文档明言「Frozen」。且本系列硬约束「不改 resolver/provider contract」。
  → **禁止字段增长**：任何新 capability 属性走 policy / metadata，不扩 contract。
- `HealthPolicy`（`ops/policy.py`）：recovery policy schema（frozen dataclass + post-init 校验）。schema 冻结、不增字段；**取值**为运营配置——出厂空 registry 是裁定，阈值经 `register_policy` 在拍板后显式填入（`:130-157`），不在代码内猜值。

→ 冻结：`CapabilityContract` 字段集（HARD）、`HealthPolicy` schema。

### Q5 — F8 → 后续阶段的 migration boundary 是什么

**裁定：F8 边界 = capability 治理自包含于 `anima/capability/`，runtime 仅经 seam 注入集成；治理是 RECORD/observer，不是执行控制方。文档化为迁移边界规则。**

- F8 治理范围：capability lifecycle / health / recovery / resolution audit。**不拥有**：task/workflow 执行语义（RFC-0002/0003）、memory（RFC-0005）、agent protocol（RFC-0004）、planning。
- 隔离机制（已就位）：
  - 治理全部落在 `anima/capability/`（governance/ + ops/ + health/ + audit/）；
  - runtime 只经注入 seam 接触治理：`lifecycle_for()` 只读访问、`audit_sink` 注入、`HealthEvidence` 发射点注入（`capability_resolver.py:263-269, :515-529`）；
  - 硬边界：`resolve()` 不读 lifecycle（QUARANTINED 仍可解析，fallback 保留）；recovery 外部驱动（无 daemon）；health 观测为注入非拉取。
- 后续阶段**不得**把治理拉进执行控制流。Convergence = 文档级边界冻结，非新代码。

→ 冻结迁移边界："governance 是旁路 RECORD/observer，runtime 仅经 seam 集成；禁止治理进入执行控制流"。

## 4. Convergence Verdict（是否需要新抽象）

**结论：仅文档级收敛（documentation-level convergence）。不需要新抽象，不需要实现。**

| 问题 | 结论 | 是否需要新抽象 |
|-|-|-|
| Q1 重复职责 | 无；三链正交 | 否 |
| Q2 RecoveryDecision | 已是 projection | 否（不新开 store） |
| Q3 三者边界 | 已冻结 | 否 |
| Q4 contract 稳定 | 均稳定/冻结 | 否（字段不增长） |
| Q5 迁移边界 | seam-based，已就位 | 否 |

三条链按设计正交共存，Convergence 的全部工作 = **冻结边界 + 文档化共存契约**。与 F8.13 授权（只读勘察、不实现）一致；本收口文档将其提升为正式 RFC 级别的边界裁定。

## 6. Continued Freeze（继续冻结）

- `ResolutionEvent` schema（不增字段）
- `HealthEvidence` schema（不增字段）
- `Lifecycle` transition semantics（`LEGAL_TRANSITIONS` 不动）
- `resolver/provider` contract（`CapabilityContract` 字段集 HARD FREEZE）
- `RecoveryDecision` 不落独立 store
- `HealthPolicy` registry 出厂为空（取值为运营配置，非代码内钉）
- 无 daemon / timer / polling（R3 贯穿全链）
- `CapabilityRegistry.lifecycle_for()` 只读、runtime 不经 governance 内联

## 7. Frozen Boundaries（硬约束延续）

- ❌ 不实现 Convergence
- ❌ 不改 ResolutionEvent schema
- ❌ 不改 HealthEvidence schema
- ❌ 不改 Lifecycle transition semantics（`LEGAL_TRANSITIONS` / `transition_to`）
- ❌ 不改 resolver/provider contract（`CapabilityContract`）
- ❌ 不引入 daemon / timer / polling

## 8. Migration Boundary（Q5 展开）

```
runtime (resolver)
   │  lifecycle_for()  ──只读──►  governance (LifecycleState)
   │  audit_sink  ─────注入────►  governance (ResolutionEvent)
   │  evidence emit ──注入────►  governance (HealthEvidence)
   ▼
resolve() 不读 lifecycle  ←── 治理是旁路 RECORD/observer，不是执行控制方
```

后续阶段（RFC-0002/0003/0004/0005 等）**不得**经由治理层注入执行控制流；治理层亦**不得**反向 import runtime。

## 9. Explicit Non-goals

本 RFC **明确不**包含以下内容（冻结边界）：

- ❌ Convergence 的任何实现 / 新抽象 / 新 store / 新 runtime layer
- ❌ ResolutionEvent 强制耐久化（保持 opt-in，F8.7）
- ❌ RecoveryDecision 独立 store
- ❌ CapabilityContract 字段扩展
- ❌ 治理进入执行控制流（违反迁移边界，§8）
- ❌ 任何 F8 之外阶段（RFC-0002/0003/0004/0005）的改动
- ❌ daemon / timer / polling

## 10. Future（ closure）

F8 系列（F8.1 → F8.13）治理能力建设已完整闭环。本 RFC 为收敛收口，**无后续 implementation slice**——后续若需调整任一冻结边界，须按项目治理流程（Foundation Evolution 协议 F1–F4）以新的 observed contradiction 提出，不得在本 RFC 上直接续改。
