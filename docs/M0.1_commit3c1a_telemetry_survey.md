## 0. 三个必须先纠正的前提

在给映射表之前，有三处与既定假设不符的事实。不先纠正，第一刀会砍偏。

### 0.1 Stage 层**不存在** `audit.emit` 调用 —— 一处都没有

批复中给出的旧形态示例：

```python
ctx.meta["core"].audit.emit(...)
```

**该形态在 `anima/pipeline/stages/` 中零出现。**

```bash
$ grep -rn "audit" anima/pipeline/stages/
(无输出)
```

`audit.emit` 的真实调用者全部在 Stage 之外：`llm/handler.py`(5)、`webui/server.py`(40+)、
`core/autonomy.py`(6)、`cognitive/*`、`tools/`、`monitors/`。这些都不是 Pipeline Stage，
不在 3c-1 范围内。

**推论：`TelemetryProtocol.emit()` 在 3c-1a 没有迁移对象。**
Stage 层的 telemetry 只有 `reply_quality` 一条线。本次只能验证 `record_*` 路径，
`emit()` 保持零消费者状态（它为 3c 之后的 handler 层迁移预留，此刻不动）。

这不是坏消息——它反而让 3c-1a 的冻结面更小、更纯。

### 0.2 `generation.py:500` 不是 telemetry 调用，是**依赖注入透传**

```python
react = ReActLoop(
    core.llm,
    available_tools,
    max_rounds=5,
    permission_level=ctx.meta.get("permission_level", 2),
    quality=getattr(core, "reply_quality", None),   # ← 这一行
    ...
)
```

它把整个 `ReplyQuality` **对象**交给 ReActLoop。ReActLoop 内部消费：

```python
# anima/agent/react.py:134-135, 190-191
self.quality.record_tool_spin(1)
self.quality.record_react_max_rounds()
```

若把它改成 `ctx.core.telemetry()`，`TelemetryProtocol` 必须立刻长出
`record_tool_spin` / `record_react_max_rounds` —— 而这两个方法的真实消费者是
**Agent 层，不是 Stage 层**。这正是批复中警惕的「不要扩大 Protocol」。

**建议：T3 排除出 3c-1a。**
它属于「Agent 声明 need」的范畴（RFC-0001），不是「Stage 使用 Facade」。
强行纳入会让 TelemetryProtocol 变成 ReplyQuality 的影子接口——换皮，不是抽象。

### 0.3 迁移后 `ctx.core` 的可用性契约有缺口（**需拍板**）

3b 的接线是**条件赋值**：

```python
# anima/llm/handler.py:1304-1305
if facade_enabled():
    ctx.core = DeprecatedCoreAccess(self.core)
```

即 `ANIMA_CORE_FACADE_ENABLED=false` 时 `ctx.core is None`。
3b 阶段无害（无人消费）。但 3c-1a 一旦让 Stage 依赖 `ctx.core`：

| flag | meta["core"] | ctx.core | 已迁移 Stage 的 telemetry |
|---|---|---|---|
| true（默认） | 在 | 在 | ✅ 正常 |
| false（回滚） | 在 | **None** | ❌ **静默丢失** |

关掉 flag 不是「回到旧世界」，而是「新路断、旧路无人走」——**回滚不完整**。
与「每个 commit 独立回滚」的纪律冲突。处理方案见 §6 决策 D1。

另：全仓 `PipelineContext(...)` 生产构造点**仅 handler.py:1285 一处**（已核实），
所以修复面很小。但 `tests/` 中有 **11 个文件**直接构造 PipelineContext。

## 3. Facade 映射

### 现状 `TelemetryProtocol`（`contracts/facades.py:47-50`）

```python
class TelemetryProtocol(Protocol):
    def record_guard_fixation(self) -> None: ...
    def emit(self, event: str, **kwargs) -> None: ...
```

### 现状实现（`contracts/access.py:97-109`）

```python
class _TelemetryFacade:
    def record_guard_fixation(self) -> None:
        rq = getattr(self._core, "reply_quality", None)
        if rq is not None:
            rq.record_guard_fixation()

    def emit(self, event: str, **kwargs) -> None:
        audit = getattr(self._core, "audit", None)
        if audit is not None:
            audit.emit(event, **kwargs)
```

### 映射结果

| ID | 目标写法 | Facade 方法 | 是否已存在 | Protocol 变更 |
|---|---|---|---|---|
| T1 | `ctx.core.telemetry().record_guard_fixation()` | `record_guard_fixation` | ✅ 已有 | **无** |
| T2 | `ctx.core.telemetry().record_context(sys, msgs)` | `record_context` | ❌ 缺失 | **+1 方法** |

**T1 是完美 1:1 映射，零 Protocol 变更。**
Facade 内部已含 `rq is None` 防御 → Stage 侧的 `getattr` + None 检查可整体删除，
代码反而变短。

## 5. AST 守护设计

### 5.1 不能做 blanket ban

`anima/pipeline/stages/` 当前有 **10 处** core 访问点，3c-1a 只消除其中 **1 处（T1）**：

| 文件 | 行 | 3c-1a 后状态 |
|---|---|---|
| `guardrail.py` | **303** | ✅ **消除** |
| `guardrail.py` | 186, 202, 313 | 保留（memory / danger / mood） |
| `generation.py` | 389, 677 | 保留 |
| `cognition.py` | 212 | 保留 |
| `memory.py` | 17 | 保留 |
| `permission.py` | 70 | 保留 |
| `_shared.py` | 103 | 保留 |

所以守护必须是**递减白名单**（allowlist that shrinks），不是一刀切禁令。
每个后续 commit 从白名单删一行——**白名单长度即迁移进度条**。

### 5.2 必须用 AST，不能用正则

本次调研中，第一版 grep 漏掉了 `guardrail.py:303`：

```python
core = (ctx.meta or {}).get("core")    # 「meta」与「.get」之间隔了 ` or {})`
```

正则 `meta\.get\(.core.\)` 匹配不到。**这本身就是必须用 AST 的证据。**

守护需覆盖至少三种形态：

```python
ctx.meta["core"]
ctx.meta.get("core")
(ctx.meta or {}).get("core")
```

### 5.3 建议实现

以 AST 遍历 `anima/pipeline/stages/*.py`，识别「字符串常量 `"core"` 作为下标或
`.get()` 首参」的节点，收集 `(文件名, 行号)`，与白名单常量比对：

```python
STAGE_META_CORE_ALLOWLIST = {
    ("guardrail.py", 186), ("guardrail.py", 202), ("guardrail.py", 313),
    ("generation.py", 389), ("generation.py", 677),
    ("cognition.py", 212), ("memory.py", 17),
    ("permission.py", 70), ("_shared.py", 103),
}
```

⚠️ **行号锚定很脆** —— 任何插入行都会让白名单失效。
建议改用**每文件计数上限**（`{"guardrail.py": 3, "generation.py": 2, ...}`），
断言「实际数 ≤ 上限」。既能防新增，又不被行号漂移误伤。见 §6 决策 D3。

`contracts/access.py` 天然在扫描范围外（不在 `stages/`），无需显式豁免。

## 6. 待拍板决策

### D1 — `ctx.core` 可用性契约（**阻塞项**）

问题见 §0.3：flag=false 时已迁移 Stage 的 telemetry 静默丢失。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A** | Stage 内双路径 `ctx.core or meta["core"]` | 与「旧路径消失」的 Step 2 直接冲突，每个迁移点拖一条永久尾巴 |
| **B** | Stage 内 `if ctx.core is None: 跳过` | 最省事，但 flag=false 时行为不等价，违反「event 内容一致」验收 |
| **C（推荐）** | handler **无条件**赋值 `ctx.core`，flag 语义反转为「是否保留 `meta["core"]`」 | 需重定义 flag（含改名） |

**推荐 C**，理由：

```python
# 无条件建立 ABI —— ctx.core 恒可用
ctx.core = DeprecatedCoreAccess(self.core)

# legacy 兼容层：3c 全量迁移后连同 flag 一起删除
if legacy_meta_core_enabled():          # 默认 true
    ctx.meta["core"] = self.core
```

这样带来三个好处：

1. **Stage 侧单路径**，无 fallback 分支，`ctx.core` 是可依赖的 ABI；
2. **回滚职责归位**：3c-1a 的回滚 = `git revert` 该 commit（commit 粒度回滚，
   与既定纪律一致），flag 不再兼任回滚开关；
3. **flag 升级为迁移进度探针** —— 关掉 legacy flag 跑全量测试，
   炸掉的每一处都是「尚未迁移的 Stage」。这比人工数 grep 可靠得多。

注意：现阶段关掉 legacy flag 会让 9 处未迁移点全炸，故**默认必须 on**，
直到 3c 全量完成。

若采纳 C，3c-1a 需含一个小改动：`handler.py:1304-1305` 改为无条件赋值 +
flag 重定义。这**动了 3b 的接线**，需要明确批准。

### D2 — T2 是否纳入 3c-1a

| 选项 | 说明 |
|---|---|
| **仅 T1**（推荐） | 冻结面最小，`TelemetryProtocol` 零变更，纯粹验证「Stage→Facade」通路 |
| T1+T2 | 一次迁完 Stage 层全部 telemetry，但需 `+record_context`，且 `generation.py:389` 仍留着，收益有限 |

**推荐仅 T1**。理由：3c-1a 的目标是**证明架构**，不是清干净。T1 单点即可完整证明
「Stage → Facade Protocol → DeprecatedCoreAccess → AnimaCore」这条链路成立。
T2 挪到 3c-1b 或与 generation 整体迁移合并，届时 `:389` 一起处理更划算。

### D3 — AST 守护粒度

| 选项 | 说明 |
|---|---|
| 行号白名单 | 精确，但任何插入行都误伤 |
| **每文件计数上限**（推荐） | 抗行号漂移，仍能防新增；迁移时下调数字 |
