## 1. The governance question

> **Who owns the canonical definition of Plan?**

Three authorities are in play. Each is described below with the five required dimensions. No preference is expressed.

---

## 2. Possible authorities

### Authority 1 — RFC-0106 Planning Authority (frozen digital-life ontology, 010x track)

- **ownership**: Declared in `docs/rfc/RFC-0106-Plan.md` §6 as the **sole constructor** of Plan (single-writer rule O1). It is the Planning Authority carried over from RFC-0105 (Goal owns adoption + lifecycle). RFC-0106 is **Anchored / Frozen** under Foundation Validation #6 — modifiable only via Foundation Evolution F1–F4.
- **invariants**: Plan = `p(Goal, Drive, Context)`; Transient-Derived (not Owned); no persistence (P3 / V4); no lifecycle (V5); the Execution Authority consumes Plan but never constructs or mutates it (§8 E4). The constitution `Plan` (`constitution/state.py:188`) is the ratified code-model of this authority — structurally aligned, transient, in-memory.
- **compatibility**: The constitution `Plan` (P1) conforms to this authority's shape. The production `AgentTask` (P2) does **not** currently declare a relationship to this authority (Study Ch2). The production runtime is not wired to this authority (zero imports of `Plan` outside `anima/constitution/`).
- **migration impact**: If this authority is canonical, any module that constructs a Plan must declare derivation from RFC-0106's Planning Authority. The production planner (`agent/planner.py`) and its output would need to state that relationship. *Conforming* to RFC-0106 modifies no Foundation document; only *changing* its invariants would require F1–F4.
- **documents affected**: `docs/rfc/RFC-0106-Plan.md` (frozen — read-only unless F1–F4); `docs/rfc/RFC-0002-Planning.md` (future — must conform, not contradict); `docs/rfc/RFC-0107-Execution.md` (consumption-side, frozen); `anima/constitution/` (already-aligned code-model).

### Authority 2 — RFC-0002 Infrastructure Planning Authority (prospective, 000x infra track)

- **ownership**: A **new** authority that RFC-0002 (000x infrastructure series, built on RFC-0001 Capability) would **establish** as the owner of the infra-track Plan definition. It does **not** inherit RFC-0106's Planning Authority; it is a separate governance body for the infrastructure track.
- **invariants**: Defined by the RFC-0002 Draft (out of scope to specify here). The Draft would declare its own Plan schema, constructor, and consumer boundary, and would state the separation of tracks so the two Plan definitions coexist without collision.
- **compatibility**: Coexists with RFC-0106 if RFC-0002 explicitly declares the boundary between the infra-track Plan and the ontology Plan (two different authorities, same word). Does not require modifying RFC-0106. May diverge in shape from P3 — the Draft decides.
- **migration impact**: No frozen document is touched. The production planner (`agent/planner.py`) and the constitution `derive_plan` would be re-pointed (in the Draft's implementation phase) to the new infra authority's contract. The frozen ontology remains as-is.
- **documents affected**: `docs/rfc/RFC-0002-Planning.md` (future — establishes the authority); possibly a track-separation note within RFC-0002; `docs/rfc/RFC-0106-Plan.md` (untouched); `docs/rfc/RFC-0107-Execution.md` (untouched).

### Authority 3 — Production TaskPlanner (de-facto, undeclared)

- **ownership**: Today, `anima/agent/planner.py:22` `TaskPlanner` is the **de-facto** constructor of plans in the running system (it produces `AgentTask.steps`). It holds no declared authority relationship to RFC-0106 or to any RFC. It is the status-quo owner by implementation, not by governance.
- **invariants**: Flat `list[Step]` (no dependency graph, no branching, no per-step tool binding per Recon §4.2). No authority-level policy is declared for the lifecycle or persistence of its output — those are resolved inside RFC-0002 Draft per the ruling on Decision B.
- **compatibility**: Does not currently align with RFC-0106 (no declared relationship) nor with the constitution model. It is the only authority actually executing in production.
- **migration impact**: If retained as canonical, RFC-0002 would formalize the production planner's output as the Plan definition and would reconcile it with whichever frozen/ontology definition exists (or explicitly override). The constitution `derive_plan` would be either deprecated or re-pointed.
- **documents affected**: `docs/rfc/RFC-0002-Planning.md` (future — would formalize this authority); `anima/agent/planner.py` (its contract would be ratified); `docs/rfc/RFC-0106-Plan.md` (possibly overridden for the infra track — would require F1–F4 only if it contradicts, not merely if it coexists separately).

## 3. Cross-authority notes (facts only, no recommendation)

- Authorities 1 and 3 currently coexist without reconciliation: production constructs plans (Authority 3) while the frozen ontology claims sole ownership (Authority 1). This is the collision the Recon (§11) and the Study (Decision A) flagged.
- Authority 2 is the only option that does not require touching the frozen ontology, because it establishes a separate track rather than challenging Authority 1.
- Authority 1's code-model (P1) is unwired; Authority 3 is wired but undeclared. Choosing either as canonical implies a wiring or declaration step — that step is implementation and is deferred to the RFC-0002 Draft per the ruling on Decisions B/C.
- No fourth authority is in scope. The constitution layer is the code rendering of Authority 1, not a separate authority.
