## 4. Findings

Five findings. Severity scale: **Major** (blocks clean downstream consumption / leaves a real
ambiguity that a later RFC could misread), **Minor** (clarity/completeness), **Editorial**
(documentation precision).

---

### F-01 — Major — `activate` transition has no corresponding Planning Interface operation

- **Severity:** Major
- **Evidence:**
  - §7.1 (line 326): *"`draft` → `active` (**activate**) — **Planning Authority only**; Workflow does
    **not** self-activate a Plan; it consumes only an `active` Plan."*
  - §7 lifecycle diagram (line 299): `[ draft ] ──► handed to Workflow (0003) ──► [ active ]`.
  - §6 Planning Interface (lines 237–269) exposes only: `request_plan`, `read_plan`, `revise_plan`,
    `list_plans`, `invalidate_plan`. There is **no `activate_plan`** (or any explicit activation)
    operation.
  - §9 E1 (line 378) shows `request_plan(...)` emitting a Plan with `status=draft`; no subsequent
    step shows how it becomes `active`.
- **Impact:** The lifecycle states that *only the Planning Authority* may move a Plan to `active`
  (§7.1), but the interface gives the Planning Authority no method to perform that move. The
  hand-off arrow in the diagram ("handed to Workflow") is not backed by any interface call. RFC-0003,
  which "consumes only an `active` Plan," has no defined trigger for the `draft → active` transition.
  This is a real gap between the lifecycle contract (§7.1) and the interface (§6).
- **Recommendation (not a design mandate — options for r1):**
  - either add an explicit `activate_plan(plan_id)` operation to the Planning Interface (Planning
    Authority only), *or*
  - clarify in §6/§7.1 that activation is performed by the Planning Authority as an implicit step of
    the hand-off (e.g. `request_plan` returns `draft`; a separate Planning-Authority action — named
    or folded into the hand-off — sets `active` before 0003 consumes it).
  - Whichever is chosen, §6 and §7.1 must name the *same* operation that performs the transition.

### F-02 — Major — Origin-agnostic producer model not reconciled with RFC-0106 V1 (anti-bypass) / O1

- **Severity:** Major
- **Evidence:**
  - RFC-0002 G5 (line 73): *"Make the `Plan` contract origin-agnostic: it may be produced by the
    Planner (0002), a Human Plan, Memory-derived planning (0004), or an external API. Workflow (0003)
    consumes the *structure*, not the producer."*
  - §5 `source` enum (line 195): `planner | human | memory | external_api`.
  - §6 "Origin-agnostic producers" (line 282): *"non-Planner producers (human, memory-derived,
    external API) emit the *same* `Plan` structure via their own interfaces. They MUST emit a
    contract-valid Plan… RFC-0003 consumes the structure regardless of `source`."*
  - §9 E4 (line 391): a human-authored plan is consumed by 0003 *identically* to a planner Plan.
  - RFC-0106 §5.2 V1 (lines 245–251): *"A direct `Plan = p'(Memory)` or `Plan = p''(Need)` that reads
    around Goal/Drive/Context is **forbidden** — it would bypass the Planning Authority's
    decomposition."*
  - RFC-0106 E3 (lines 477–481): `plan.from_recent_episodes(recent)` is **rejected** — experience
    must sediment to Memory → reshape Goal → Planning Authority constructs Plan.
  - RFC-0106 §6.1 / §6.2: *only the Planning Authority may construct Plan* (single-writer rule O1).
- **Impact:** RFC-0002 claims "semantic alignment" with RFC-0106 (§0/§4) and states the Planning
  Authority is the *sole* constructor (§4.1, §6 Authority boundary). But its own `source != planner`
  producer model lets human / memory / external_api emit a *contract-valid canonical Plan* that
  0003 consumes identically — without any stated role for the Planning Authority in that emission.
  Read literally, a `source=memory` Plan *is* `Plan = p'(Memory)`, the exact V1 bypass RFC-0106
  rejected. The alignment narrative is **incomplete**: RFC-0002 never states how a non-planner Plan
  is reconciled with "only the Planning Authority constructs Plan." Left unstated, a future
  RFC-0004 (Memory) or RFC-0005 (Multi-Agent) could read `source=memory/external_api` Plans as fully
  canonical and emit them directly — re-introducing the O1 Authority-leak RFC-0106's V3 was built to
  prevent.
- **Recommendation (for r1 to state explicitly — not a design mandate):**
  - Add a short paragraph in §4 or §6 clarifying the relationship between `source != planner` Plans
    and RFC-0106's sole-constructor rule. Two coherent options (pick one in r1):
    1. Non-planner Plans are *advisory input structures*; the Planning Authority must ratify/construct
       the canonical Plan from them before 0003 may consume it (preserves O1 strictly), **or**
    2. `source != planner` Plans are consumed by 0003 as pre-formed structures but are explicitly
       *not* "canonical Plans" in RFC-0106's ontological sense — only `source=planner` Plans are, and
       the contract's `source` field marks the distinction.
  - Either way, the text must make clear that allowing non-planner producers does **not** rescind
    RFC-0106's V1/O1.

### F-03 — Editorial — RFC-0106 citation precision in §4.1

- **Severity:** Editorial
- **Evidence:**
  - §4.1 row (line 123): *"Plan **reads** Goal/Drive/Context as signals, mutates none (§5.1, V3 C2)."*
  - In RFC-0106, "reads as signals, mutates none" is §5.1 (lines 191–202). The **V3 C2** authority
    boundary clarification ("Planning Authority governs plan construction, not Goal mutation, not
    Drive mutation") is located in **§6.2** (lines 327–376), not §5.1.
- **Impact:** Minor — a reader verifying the citation will not find V3 C2 at §5.1. Does not change
  meaning, but reduces the auditability the governance trail is meant to provide.
- **Recommendation:** Split/correct the citation to `§5.1 (read-only signals) / §6.2 (V3 C2
  authority boundary)`, or cite §6.2 alone for the "mutates none" claim.

---

### F-04 — Minor — Planning Interface wording slightly conflates Authority and implementation

- **Severity:** Minor
- **Evidence:**
  - §6 intro (line 233): *"The Planning Interface is the stable API the **Planning Authority's
    implementation** (the Planner; M1.6 `construct_plan`) exposes."*
  - RFC-0106 §6.1 (lines 323–325) carefully distinguishes: *"This authority is a semantic contract…
    The Planning Pipeline / Planner that runs the construction is an **implementation** of that
    contract, not the authority."*
- **Impact:** RFC-0002's phrasing reads as if the Interface *is* exposed by the Authority's
  implementation, quietly merging "Authority (owner)" with "Planner (implementation)." RFC-0002 §4.2
  correctly says it does *not* redefine the Authority's ontological ownership, so the §6 wording is a
  small inconsistency with RFC-0106's own distinction and with §4.2.
- **Recommendation:** Reword to keep the three roles distinct — e.g. *"The Planning Interface is the
  stable contract surface the Planning Authority exposes; its implementation (the Planner, M1.6
  `construct_plan`) realizes that surface."* No change to meaning, sharper alignment with RFC-0106
  §6.1.

---

### F-05 — Minor — `deprecated` Plan leaves no stated re-plan path

- **Severity:** Minor
- **Evidence:**
  - §7 / §7.1: a `deprecated` Plan is *"MUST NOT be consumed… discarded, never restored"* (lines 309,
    317, 328). Deprecation is triggered by "Goal cancelled / context stale" with *no replacement
    implied*.
  - G4 (line 70): Plan is *recomputed, never restored* — a fresh Plan is always permissible.
- **Impact:** The lifecycle states a deprecated Plan is never restored, but does not state whether a
  *future* `request_plan` for the same (later re-opened) Goal is allowed after deprecation. Given G4
  (transient, recomputed), it should be — but the text doesn't say so, leaving a small gap a
  downstream reader could misread as "once deprecated, the Goal can never get a Plan again."
- **Recommendation:** One clarifying sentence in §7.1: *"Deprecating a Plan does not block a later
  `request_plan` for the same Goal — a fresh Plan is always recomputable per G4."*
