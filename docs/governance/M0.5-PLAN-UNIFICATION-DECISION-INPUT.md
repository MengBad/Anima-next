## Decision A — Canonical Plan definition & cross-track authority collision

**要决定什么**: Which of the three existing Plan definitions (P1 constitution `Plan`, P2 production `AgentTask.steps`, P3 RFC-0106 ontology `Plan`) is canonical for RFC-0002 — or whether an infra-track representation distinct from all three is required. And, if P3 is chosen or referenced, whether RFC-0002 (000x infrastructure series) **inherits** RFC-0106's frozen Planning Authority or defines a **separate** infrastructure Planner.

**事实 (from Recon/Study)**:
- P1 (`constitution/state.py:188`) models P3's shape but is **unwired** (zero production imports; only `constitution/` + `tests/` read it).
- P2 (`agent/state.py:19-40`) is production-wired, persisted to `data/agent_tasks.json`, carries an Owned-style lifecycle; does not match P3's transient/no-store rule.
- P3 (`docs/rfc/RFC-0106-Plan.md`) is **Anchored / Frozen** (Foundation Validation #6), modifiable only via Foundation Evolution F1–F4. It defines Plan as Transient-Derived, no persistence, Planning Authority as sole constructor (§6).
- RFC-0002 and RFC-0106 belong to **different governance tracks** (000x infra vs 010x digital-life ontology) but share the words Plan / Workflow / Execution with different authority boundaries (Recon §11).

**涉及对象**: RFC-0002 (draft pending), RFC-0106 (frozen), RFC-0100 §1.15/§1.16, Planning Authority (RFC-0106 §6), `anima/constitution/`, `anima/agent/`.

**影响范围**: RFC-0002's first stated focus ("define what a Plan is"), its Planning Interface output schema, and whether the draft may proceed without touching the frozen ontology. This is the single item the Recon (§11) and Study (Ch4 Q2) flag as able to **reshape RFC-0002's boundary**.

**哪些文档会受影响**:
- If RFC-0002 adopts P3 or references RFC-0106's Planning Authority: `docs/rfc/RFC-0002-Planning.md` (future) must not contradict RFC-0106; it may need an explicit cross-reference or carve-out.
- If RFC-0002 defines a separate infra Planner: no change to RFC-0106, but `docs/rfc/RFC-0002-Planning.md` must explicitly state the separation of tracks.
- If a fourth representation is required: a Foundation Evolution RFC (F1–F4) may be required to amend RFC-0106, since P3 is frozen.

**如果保持现状（不决定）会发生什么**: RFC-0002 Draft would begin without a settled canonical definition. Given P1/P2/P3 already coexist and P3 is frozen, the Draft risks either (a) contradicting RFC-0106's transient/no-store classification, or (b) introducing a **fourth** Plan definition — exactly the outcome the Recon warned against. The Draft cannot converge.

**选项影响（非推荐）**:
- 如果治理层裁定 RFC-0002 可定义独立的 infra-track Planner（不继承 RFC-0106 的 Planning Authority）：RFC-0002 可在不与冻结本体冲突的前提下起草，但须显式声明两条轨道的边界。
- 如果治理层裁定 RFC-0002 必须继承 RFC-0106 的 Planning Authority：RFC-0002 的 Plan 定义受冻结本体约束，任何偏离需先走 Foundation Evolution F1–F4。
- 如果治理层裁定需要统一到 P3 且修改 P2 的持久化语义：触发 Foundation Evolution 流程，RFC-0002 在该裁定前无法定稿。

## Decision B — Persistence boundary (Plan vs Execution Task Record)

**要决定什么**: Whether the persisted production record `AgentTask` (`data/agent_tasks.json`, `agent/state.py:70-93`) is a **distinct concept** ("Execution Task Record") from the transient Plan (P3: no persistence), or whether it *is* the Plan under a different name. This determines whether P2's persistence + lifecycle is legitimate or a mis-classification under P3.

**事实 (from Recon/Study)**:
- P3 explicitly forbids Plan persistence (P3 / V4): no `Plan.save()`, no `plans.json`. Plan is constructed each time, discarded after Execution consumes it (V5).
- P2 persists all tasks to `agent_tasks.json`; on restart, `status == "executing"` is re-marked `failed` (`state.py:81-84`) — the persisted record is authoritative across restarts.
- P2 carries an Owned-style lifecycle (`planning|executing|completed|failed|cancelled`); P3 asserts Plan has **no** lifecycle (Study Ch2 ownership conflict).
- Under P3's classification, "a persisted Plan store" is exactly the mis-classification P1 warns against (§8: "NOT Owned", "no `plans.json` store") and an O1 single-writer violation (Study Ch2).

**涉及对象**: `AgentTaskStore` (`agent/state.py:70-93`), `AgentExecutor`, `OwnerTaskAgent`, RFC-0106 §8 (consumption rule), RFC-0004 (Memory, future).

**影响范围**: Whether RFC-0002 must **rename/reframe** `AgentTask.steps` as an execution record (separate from Plan), and whether the in-flight multi-step task persistence is legitimately a non-Plan concept. Affects RFC-0002's "Plan lifecycle" item and RFC-0004's input shape (Q7).

**哪些文档会受影响**:
- `docs/rfc/RFC-0002-Planning.md` (future): if Plan ≠ AgentTask, the draft must define Plan as transient and explicitly place persistence under a separate "Execution Task Record" concept (likely RFC-0003's concern).
- `docs/rfc/RFC-0106-Plan.md`: if the ruling is that AgentTask *is* the Plan, P3's no-persistence rule is overridden for the infra track → Foundation Evolution required.
- `docs/rfc/RFC-0004-Memory.md` (future): its input shape (outcome→Memory) depends on whether Plan is transient (P3) or AgentTask is persisted (P2).

**如果保持现状（不决定）会发生什么**: RFC-0002 faces an ambiguous object — it cannot state whether its "Plan" persists. If it adopts P2's shape wholesale, it silently contradicts P3's no-store rule; if it adopts P3's transience, it leaves in-flight multi-step tasks with no stated home. The Draft's persistence section becomes internally inconsistent.

**选项影响（非推荐）**:
- 如果治理层裁定 `AgentTask` 是独立于 Plan 的 "Execution Task Record"：RFC-0002 可将 Plan 定义为瞬时派生（对齐 P3），持久化归属 RFC-0003/执行层，无需修改冻结本体。
- 如果治理层裁定 `AgentTask.steps` 即 Plan 本身：P3 的 no-persistence 规则在 infra 轨被覆盖，需 Foundation Evolution 修改 RFC-0106。
- 如果保持两套并存且不声明关系：RFC-0002 与 RFC-0106 在持久化语义上形成隐性冲突，后续 RFC-0004/0003 将继承该歧义。

## Decision C — Governance ratification mechanism (Foundation Evolution precondition)

**要决定什么**: Whether resolving Decision A and B requires **modifying the frozen ontology** (RFC-0106/0107, via Foundation Evolution F1–F4) as a precondition for RFC-0002, or whether RFC-0002 may proceed as a **parallel infra-track definition** that does not touch the frozen documents. This is the meta-decision that determines whether RFC-0002 is blocked.

**事实 (from Recon/Study)**:
- RFC-0106 and RFC-0107 are **Anchored / Frozen**; the only modification path is Foundation Evolution F1–F4 (Study Ch1 P3; Recon §11).
- The `Plan.branching`/`Plan.rollback` fields (`constitution/state.py:201-202`) are RFC-0106's reserved interface points for Workflow; RFC-0107 explicitly does not implement them (Recon §11). This empty space is RFC-0003's landing spot, not RFC-0002's.
- The Roadmap (frozen) already separated RFC-0002 (Planning) from RFC-0003 (Workflow) and placed advanced reasoning outside the numbered series (r1 ruling).

**涉及对象**: Foundation Evolution Protocol (F1–F4), RFC-0106, RFC-0107, RFC-0002 (pending), M0.5 Roadmap (frozen).

**影响范围**: The **sequencing** of the entire M0.5 infra track. If a Foundation Evolution is required first, RFC-0002 is blocked until that裁定 lands. If a parallel infra-track definition is permitted, RFC-0002 can start now.

**哪些文档会受影响**:
- If Foundation Evolution required: a new `docs/rfc/RFC-01xx` (Foundation Evolution) would be created/anchored before RFC-0002 Draft.
- If parallel infra-track permitted: only `docs/rfc/RFC-0002-Planning.md` (future) is created, with an explicit track-separation statement; RFC-0106/0107 untouched.

**如果保持现状（不决定）会发生什么**: The Draft cannot start, because the author cannot know whether to write against the frozen ontology (risking contradiction) or against a separate infra track (requiring an explicit carve-out the reviewer hasn't authorized). This is the precise state the governance cadence has maintained: RFC-0002 Draft is deferred until the governance layer rules.

**选项影响（非推荐）**:
- 如果治理层裁定 RFC-0002 可平行于冻结本体起草（infra-track Plan ≠ ontology Plan）：RFC-0002 不阻塞，可直接启动 Draft，并显式声明轨道分离。
- 如果治理层裁定必须先调和冻结本体：RFC-0002 阻塞，须先发起 Foundation Evolution F1–F4 裁定，再起草。

## 5. RFC-0002 是否仍被阻塞？

**YES.**

**阻塞原因**: Decision A（canonical Plan 定义 + 跨轨 authority 碰撞）与 Decision C（是否需先修改冻结本体 RFC-0106/0107）共同构成一个治理层尚未裁定的前置条件。RFC-0106/0107 为 Anchored/Frozen，唯一修改路径是 Foundation Evolution F1–F4；RFC-0002 若不明确其 Plan 定义是否继承冻结本体的 Planning Authority、是否可平行于冻结本体起草，Draft 将在「与冻结本体冲突」或「发明第四个 Plan」之间二选一——二者均为 Recon 明确警示的风险。该裁定不在 RFC-0002 起草流程的能力范围内，必须由治理层（用户）做出。

**可留到 RFC 内解决的问题**: Q5（workflow 形状，归 RFC-0003）、Q6（状态枚举统一，RFC-0002 内部实现）、Q7（Memory 输入形状，归 RFC-0004）、Q9（constitution 接入成本，RFC-0002 内部实现）。这些不构成治理阻塞。

一旦治理层就 Decision A / B / C 给出裁定，RFC-0002 Draft 即可启动；若裁定为「平行于冻结本体起草」，则 Draft 不依赖任何 Foundation Evolution 前置。

## Reviewer Ruling (2026-08-07)

Per reviewer ruling on this Decision Input:

- **Decision A (Canonical Plan authority)** — **BLOCKING**. Must be decided before RFC-0002 Draft. If the owner of Plan's definition is unknown, RFC-0002 risks creating a fourth Plan type and cascading confusion into Workflow / Memory.
- **Decision B (Persistence boundary)** — **NON-BLOCKING**. A question RFC-0002 itself should answer (what is Plan, what is AgentTask, which persists). Does not affect Foundation. Resolved inside the Draft.
- **Decision C (Foundation-precondition)** — **NON-BLOCKING / Agent's final verdict overturned**. "Foundation Frozen" means Foundation may not be modified surreptitiously; it does **not** prevent drafting a new RFC. Correct flow: Draft RFC-0002 → if it requires a Foundation change, RFC-0002 annotates "Requires Foundation Evolution (F1/F2)" → await Foundation decision. Drafting does **not** require prior Foundation modification.

**Consequence**: RFC-0002 is **no longer blocked**. The only open governance question is Decision A — *Who owns the canonical definition of Plan?*

**Next step**: `PLAN-AUTHORITY-STUDY.md` (Decision A only) compares the candidate authorities and ends with "Decision Required: Choose the canonical owner of Plan." After that study, the governance decision is made and RFC-0002 Draft begins.
