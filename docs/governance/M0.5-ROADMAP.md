# M0.5 Roadmap — From Tool-Calling to Sustained Complex-Task Execution

**Status:** DRAFT (roadmap only — no RFC drafted, no code)
**Branch:** `m0.5-roadmap` (branched from `m0.4.8-pilot-rfc @ 18d6300`; M0.4.x left frozen pending human approval)
**Prerequisite:** RFC-0001 Capability Layer (M0.4.x) — provides the capability substrate M0.5 consumes.
**Author:** Anima engineering (drafted for governance review)
**Classification:** Planning document. **NOT an RFC. NOT implementation.**

---

## 1. Why M0.5

M0.4.x established that Anima can *safely gate and route* a capability (D-A0–D-A4, default OFF, controlled Pilot A). That is infrastructure. It answers *"can the agent reach a tool, and who is allowed?"*

It does **not** answer: *given a messy, multi-step, long-running goal, can the agent figure out what to do, do it step by step, survive interruptions, remember what it learned, and enlist help?*

M0.5's thesis:

> **Evolve the Agent from "can call tools" to "can sustain complex tasks end-to-end."**

This is the difference between a function-calling wrapper and an agent that actually completes work. It is the natural next layer above the capability substrate.

## 2. Where M0.5 sits

```
RFC-0001 Capability Layer   (M0.4.x — DONE, substrate)
        │  provides: need → resolver → provider, gated + observable
        ▼
M0.5 Cognition / Execution Layer
        ├─ RFC-0002 Planning      (WHAT to do, in what order)
        ├─ RFC-0003 Workflow      (HOW to run multi-step, recoverably)
        ├─ RFC-0004 Memory        (what it knows / remembers)
        └─ RFC-0005 Multi-Agent   (delegating across roles)
```

M0.5 **consumes** RFC-0001; it does not modify it. No capability/provider is added by M0.5 — only how the agent *orchestrates* existing capabilities.

## 3. Planned RFCs

### RFC-0002 — Planning
- **Goal:** Decompose a goal into steps; maintain long- and short-term plans; produce a structure that execution can follow and *resume* after interruption.
- **Boundary (in):** goal → task graph / step list; prioritization; dependency ordering; plan versioning; recoverable checkpointing of plan state.
- **Boundary (out):** the *runtime* execution of steps (RFC-0003); the *memory* the plan reads/writes (RFC-0004); actually calling providers (RFC-0001).
- **Depends on:** RFC-0001 (to know which capabilities exist).

### RFC-0003 — Workflow
- **Goal:** Execute multi-step processes with conditional branching, retries, and durable state.
- **Boundary (in):** step runtime; conditional / loop control; retry with backoff; persistence of run state; crash recovery.
- **Boundary (out):** *deciding* the steps (RFC-0002); *memory* of outcomes (RFC-0004); *agent collaboration* (RFC-0005).
- **Depends on:** RFC-0002 (consumes its plan format).

### RFC-0004 — Memory
- **Goal:** Distill experience, retrieve relevant knowledge, compress context for long tasks.
- **Boundary (in):** experience / skill capture; semantic + episodic retrieval; context-window management / summarization; durability.
- **Boundary (out):** the planning logic that *uses* memory; the workflow that *writes* results back (those call into this).
- **Depends on:** none (substrate); usable by 0002 / 0003 / 0005.

### RFC-0005 — Multi-Agent
- **Goal:** Collaborate across agents with role division and task delegation.
- **Boundary (in):** role / specialization definitions; delegation protocol; result aggregation; isolation between agents.
- **Boundary (out):** single-agent planning (0002) and workflow (0003) — Multi-Agent *orchestrates* them, does not reimplement them.
- **Depends on:** 0002 + 0003 + 0004 (it delegates plans, runs them as workflows, and shares memory).

## 4. Proposed sequencing (for ratification, not yet decided)

```
0002 Planning  ─┐
               ├─► 0003 Workflow  ─┐
0004 Memory   ─┘                   ├─► 0005 Multi-Agent
                                   ┘
```
- 0002 and 0004 can start in parallel (both foundational, low coupling).
- 0003 follows 0002 (needs the plan format).
- 0005 is last (needs all three).

This is a *proposal*; the reviewer may reorder.

## 5. Explicitly OUT of scope for M0.5

- **F2 / execution governance** — opening `code.execute` real execution remains a separate, gated decision (Pilot B). M0.5 plans and workflows operate over already-gated capabilities.
- **Reasoning Engine** (Tree Search / Self-Consistency / Debate / Reflection-on-reasoning) — discussed in earlier V2 notes but **not** one of the four RFCs; deferred to a later track (M0.6 or beyond). M0.5 uses the LLM as-is for planning / inference.
- **New capabilities / providers** — RFC-0001 is the substrate; M0.5 adds no provider.
- **Capability-layer changes** — M0.4.x is frozen; M0.5 consumes it unchanged.
- **Migration from V1 (RFC-0000)** — already handled; not revisited.
- **Fine-tuning / model swaps / training** — outside scope.
- **Sandbox / isolation hardening** — F2 / Pilot B territory.
- **WebUI feature work** — only observability hooks if strictly needed.

## 6. Governance cadence (same as M0.4.x)

Each RFC follows: **Draft → Independent Review → r-revision → Decision Package → Human Approval → Implementation (if approved)**. No RFC proceeds to code without the human's approval gate. Document iteration stops at the Decision Package; the agent does not skip Review → Approval.

## 7. Continuity with the earlier LIMBot V2 sketch

The prior V2 plan enumerated RFC-0002 Task / 0003 Workflow DSL / 0004 Agent Protocol / 0005 Memory. M0.5 **reframes** that:

- *Task* → *Planning* (planning is broader than a static DAG; includes prioritization + recovery).
- *Agent Protocol* → *Multi-Agent* (collaboration / delegation focus).
- *Workflow DSL* → *Workflow* (runtime + persistence, not just a DSL).
- *Memory* unchanged in intent.

Numbering is preserved (0002–0005). Reasoning Engine, previously a philosophy component, is now explicitly deferred.
