# M0.5 Roadmap — From Tool-Calling to Sustained Complex-Task Execution

**Status:** APPROVED BASELINE (frozen — no further roadmap revision without explicit reopening by the reviewer)
**Branch:** `m0.5-roadmap`
**Prerequisite:** RFC-0001 Capability Layer (M0.4.x) — provides the capability substrate M0.5 consumes.
**Author:** Anima engineering (drafted for governance review; r1 per reviewer ruling 2026-08-07)
**Classification:** Planning document. **NOT an RFC. NOT implementation.**

---

## 1. Why M0.5

M0.4.x established that Anima can *safely gate and route* a capability (D-A0–D-A4, default OFF, controlled Pilot A). That is infrastructure. It answers *"can the agent reach a tool, and who is allowed?"*

It does **not** answer: *given a messy, multi-step, long-running goal, can the agent figure out what to do, do it step by step, survive interruptions, remember what it learned, and enlist help?*

M0.5's thesis:

> **Evolve the Agent from "can call tools" to "can sustain complex tasks end-to-end."**

This is the difference between a function-calling wrapper and an agent that actually completes work. It is the natural next layer above the capability substrate.

## 2. Where M0.5 sits

```
RFC-0001 Capability Layer   (M0.4.x — DONE, substrate)
        │  provides: need → resolver → provider, gated + observable
        ▼
M0.5 Cognition / Execution Layer
        ├─ RFC-0002 Planning      (WHAT to do, in what order)
        ├─ RFC-0003 Workflow      (HOW to run multi-step, recoverably)
        ├─ RFC-0004 Memory        (what it knows / remembers)
        └─ RFC-0005 Multi-Agent   (delegating across roles)
```

M0.5 **consumes** RFC-0001; it does not modify it. No capability/provider is added by M0.5 — only how the agent *orchestrates* existing capabilities.

## 3. Architectural Principles

The following principles govern **every** RFC in M0.5. Individual RFCs reference these instead of restating them.

1. **Each RFC solves exactly one problem.** A capability belongs in one RFC; if two RFCs need it, it is a shared substrate (e.g. RFC-0001) or a stable interface, not a duplicated mechanism.
2. **Every RFC must be independently reviewable.** It has a self-contained goal, boundary, and acceptance criteria; its approval does not depend on another RFC being merged first. (It may *depend on* another at runtime, but the contract it depends on is stable.)
3. **No cross-RFC modification of an existing Contract.** Once an RFC is ratified, its contracts (schemas, interfaces, invariants) are frozen; later RFCs connect *through* those contracts, they do not rewrite them. (Mirrors the M0.4.x Foundation-stability rule.)
4. **New capability connects only through a stable interface.** RFCs discover and compose each other via published interfaces (e.g. the `Plan` contract between 0002 and 0003), not via internal mutation.
5. **Implementation never precedes governance.** No code is written before the RFC is drafted, independently reviewed, revised, and human-approved. Document iteration stops at the Decision Package.

## 4. Planned RFCs

### RFC-0002 — Planning
- **Goal:** Decompose a goal into steps; maintain long- and short-term plans; produce a structure that execution can follow and *resume* after interruption.
- **Boundary (in):**
  - Goal decomposition → task graph / step list.
  - Prioritization; dependency ordering; plan versioning; recoverable checkpointing of plan state.
  - **Plan representation** — the concrete schema/format of a `Plan` (the interface contract 0003 consumes).
  - **Planning interface** — the stable API other RFCs call to request / read / update a plan.
- **Boundary (out):**
  - *Runtime* execution of steps (RFC-0003).
  - *Memory* the plan reads/writes (RFC-0004).
  - Actually calling providers (RFC-0001).
  - **Advanced reasoning** — CoT, Tree Search, Reflection, Self-critique. The *interface* for planning is in scope; the *advanced reasoning strategies* that may later drive it are **NOT** (deferred, no numbered RFC in M0.5).
- **Depends on:** RFC-0001 (to know which capabilities exist).

> **Note (per reviewer ruling):** Planning *is* a form of reasoning. M0.5 fixes the **Planning Interface** now (RFC-0002) so that later advanced-reasoning strategies can plug in without redefining the contract. The strategies themselves are deferred.

### RFC-0003 — Workflow
- **Goal:** Execute multi-step processes with conditional branching, retries, and durable state.
- **Boundary (in):** step runtime; conditional / loop control; retry with backoff; persistence of run state; crash recovery.
- **Boundary (out):** *deciding* the steps (RFC-0002); *memory* of outcomes (RFC-0004); *agent collaboration* (RFC-0005).
- **Depends on:** RFC-0002 — **consumes the `Plan` contract** (the interface 0002 publishes).
- **Decoupling note (per reviewer ruling):** Workflow consumes a `Plan` *structure*, not a Planner. The plan may originate from the Planner (0002), a Human Plan, Memory-derived planning (0004), or an external API. Workflow must not assume the Planner produced it.

### RFC-0004 — Memory
- **Goal:** Distill experience, retrieve relevant knowledge, compress context for long tasks.
- **Boundary (in):** experience / skill capture; semantic + episodic retrieval; context-window management / summarization; durability.
- **Boundary (out):** the planning logic that *uses* memory; the workflow that *writes* results back (those call into this).
- **Depends on:** none (substrate); usable by 0002 / 0003 / 0005.

### RFC-0005 — Multi-Agent
- **Goal:** Collaborate across agents with role division and task delegation.
- **Boundary (in):** role / specialization definitions; delegation protocol; result aggregation; isolation between agents.
- **Boundary (out):** single-agent planning (0002) and workflow (0003) — Multi-Agent *orchestrates* them, does not reimplement them.
- **Depends on:** 0002 + 0003 + 0004 (it delegates plans, runs them as workflows, and shares memory).

## 5. RFC dependency graph

```
          RFC-0004
            Memory
               │
               │  (read / write by)
               ▼
RFC-0002 ─────────► RFC-0003
 Planning          Workflow
  │ produces         │ consumes
  │  Plan            │  Plan
  └──────────┐       │
             ▼       ▼
         RFC-0005
        Multi-Agent
```

Reading the graph:
- **0004 (Memory)** is a substrate: 0002 / 0003 / 0005 read and write it. It depends on nothing in M0.5.
- **0002 (Planning)** *produces* the `Plan` contract; **0003 (Workflow)** *consumes* it.
- **0003** depends on 0002 **only through the `Plan` interface** — not through the Planner implementation. This is the healthy "produces / consumes" boundary the reviewer confirmed.
- **0005 (Multi-Agent)** sits on top of all three: it delegates plans (0002), runs them as workflows (0003), and shares memory (0004).

## 7. Explicitly OUT of scope for M0.5

- **F2 / execution governance** — opening `code.execute` real execution remains a separate, gated decision (Pilot B). M0.5 plans and workflows operate over already-gated capabilities.
- **Advanced reasoning** (CoT / Tree Search / Self-Consistency / Debate / Reflection-on-reasoning) — **NOT part of M0.5**. The *Planning Interface* (a stable API + `Plan` contract) belongs to RFC-0002; the *advanced reasoning strategies* that may later drive planning are explicitly deferred and have **no numbered RFC** in M0.5 (previously floated as "M0.6", now withdrawn as a standalone track).
- **New capabilities / providers** — RFC-0001 is the substrate; M0.5 adds no provider.
- **Capability-layer changes** — M0.4.x is frozen; M0.5 consumes it unchanged.
- **Migration from V1 (RFC-0000)** — already handled; not revisited.
- **Fine-tuning / model swaps / training** — outside scope.
- **Sandbox / isolation hardening** — F2 / Pilot B territory.
- **WebUI feature work** — only observability hooks if strictly needed.

## 8. Governance cadence (same as M0.4.x)

Each RFC follows: **Draft → Independent Review → r-revision → Decision Package → Human Approval → Implementation (if approved)**. No RFC proceeds to code without the human's approval gate. Document iteration stops at the Decision Package; the agent does not skip Review → Approval.

## 9. Continuity with the earlier LIMBot V2 sketch

The prior V2 plan enumerated RFC-0002 Task / 0003 Workflow DSL / 0004 Agent Protocol / 0005 Memory. M0.5 **reframes** that:

- *Task* → *Planning* (planning is broader than a static DAG; includes prioritization + recovery).
- *Agent Protocol* → *Multi-Agent* (collaboration / delegation focus).
- *Workflow DSL* → *Workflow* (runtime + persistence, not just a DSL).
- *Memory* unchanged in intent.

Numbering is preserved (0002–0005). The *Planning Interface* is now owned by RFC-0002; advanced Reasoning is explicitly deferred **without a number**. No new capability/provider is introduced by M0.5.

## 10. Open questions (resolved + remaining)

**Resolved by reviewer ruling (2026-08-07):**

- **Q1 — Should Reasoning get a separate numbered RFC?** **No.** Advanced reasoning (CoT / Tree Search / Reflection / Self-critique) is deferred; the *Planning Interface* is absorbed into RFC-0002. No new number.
- **Q2 — Merge 0002 + 0003 into one Execution RFC?** **No.** Keep them separate: 0002 answers *"what to do"*, 0003 answers *"how to execute step by step"*. The `Plan` is the interface contract between them; Workflow consumes the `Plan` *structure*, not the Planner.

**Remaining (to be resolved within their respective RFCs, not blockers for the roadmap):**

- **Q3 — Does Multi-Agent (0005) need a separate "Agent Protocol" RFC?** Open; decided when 0005 is drafted.
- **Q4 — Any capability the agent lacks *today* that would block even *planning* a real task?** If yes, that is an RFC-0001 gap, not M0.5.
