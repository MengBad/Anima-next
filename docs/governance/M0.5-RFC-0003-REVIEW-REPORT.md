## Findings

### F-01 — Orphan reference fields: `goal_ref` / `context_ref` / `budget_ref` have no sourcing operation  ·  **Major**

- **Location:** §5 `WorkflowRun` contract (lines 219 `goal_ref`, 227 `budget_ref`, 228
  `context_ref`) + §6 `WorkflowInterface.start_run(self, plan_ref: str)` (line 273).
- **Issue:** The contract declares `goal_ref`, `context_ref`, `budget_ref` as run fields, but
  `start_run` accepts **only** `plan_ref`. No interface operation populates these refs. Yet
  `goal_ref` is explicitly "for 0004/0005" (line 219) — i.e. a downstream RFC consumes it. Without
  a defined population path, RFC-0004/0005 consumers cannot rely on `goal_ref` being present, and
  implementations will diverge on where it comes from. This is the same break class as RFC-0002
  F-01 (a field exists in the contract, but no operation supplies it).
- **Recommendation:** Pin the population path in the contract. Either (a) `start_run` accepts
  optional `goal_ref` / `context_ref` / `budget_ref` parameters, or (b) §5/§6 state that the
  executor derives `goal_ref` from the Plan (Plan → Goal ref) and sets `context_ref` /
  `budget_ref` at run start. The field must not be declared with an undefined source.

### F-02 — `plan_ref` reference semantics undefined against a Transient Plan  ·  **Major**

- **Location:** §5 `plan_ref: string` ("ref to the ACTIVE Plan this run executes, read-only",
  line 218) + §4.1 ("Plan is Transient-Derived, never stored", line 143) + §7.1 / Example E3
  (lines 437–440: crash → `request_plan(G1)` recomputes a **fresh** Plan P1' with a new id →
  `start_run(P1')` creates a **fresh** run R1').
- **Issue:** `plan_ref` is presented as a ref to "the ACTIVE Plan". But the ontology fixes Plan as
  Transient-Derived (discarded after the run), and E3 shows that on crash a *new* Plan (new id) and
  a *new* run are created. Therefore a **persisted** run's `plan_ref` points to a Plan that no
  longer exists. The contract treats `plan_ref` as a live foreign key, but the ontology guarantees
  the target is evanescent. An implementer who builds a referential-integrity join to a never-
  persisted object will produce broken recovery logic.
- **Recommendation:** Define `plan_ref` explicitly as a **captured opaque handle** — plan id +
  `Plan.contract_version` snapshot taken at run-creation — and state that it is **not** a live
  pointer to a stored Plan entity. One clarifying sentence in §5 resolves it.

### F-03 — `pending` state has no abort / terminal exit  ·  **Major**

- **Location:** §7 lifecycle diagram (lines 335–356) + §7.1 transition table (`pending → running`
  only, line 374; `running|suspended → failed|cancelled`, line 378).
- **Issue:** `pending` transitions **only** to `running` via "first dispatch". `cancel_run` is
  scoped `running|suspended → cancelled` — `pending` is excluded. If first dispatch never occurs
  (process crash before dispatch, or a Plan with **0 tasks**), the run is orphaned in `pending`:
  no `cancel`, no `completed`. The lifecycle is incomplete at its **entry** state.
- **Recommendation:** Add an exit for `pending` — at minimum `pending → cancelled` (Authority
  abort before dispatch) — and/or define empty-Plan handling (`start_run` rejects a 0-task Plan, or
  transitions `pending → completed` immediately). This closes the lifecycle.

### F-04 — Run-level `failed` trigger from Task-level `failed` is unspecified  ·  **Minor**

- **Location:** §7 state table (line 364: "failed: Terminal failure … retries are per-Task impl")
  + §6 `report_task_outcome` (line 308: "running → failed on terminal failure").
- **Issue:** What makes a single Task `failed` *terminal for the run*? Per-Task `attempts` / retry
  is an implementation concern (§8 GQ5), and `branching` / `rollback` may recover a failure. The
  contract never states the criterion for `running → failed` (e.g. "a Task fails with no remaining
  retry / branch path") nor for `running → completed` ("all TaskStates ∈ {done, skipped}"). It is
  only implied.
- **Recommendation:** State the completion / failure criterion explicitly in §6/§7 (Authority
  transitions `running → completed` when every TaskState ∈ {done, skipped}; `running → failed`
  when a Task fails and no `branching` / `rollback` / retry path remains).

### F-05 — Missing invariant linking `current_task_id` ↔ `task_states`  ·  **Minor**

- **Location:** §5 `current_task_id` (line 223, "which Task is in progress (resume anchor)") +
  `task_states` (line 222).
- **Issue:** Both fields are declared, but no invariant connects them. On `running`, is
  `current_task_id` non-null and equal to the unique TaskState with status = `running`? On
  `suspend`, does `current_task_id` still point at the in-progress task? Unspecified →
  implementations can desync the resume anchor from actual progress, breaking crash-resume.
- **Recommendation:** Add an invariant clause (§5 or §7): at most one TaskState has status =
  `running`; `current_task_id` references it; `current_task_id` is non-null iff run status ∈
  {running, suspended}.

### F-06 — `ExecutionResult` lacks `contract_version`  ·  **Minor**

- **Location:** §5 `ExecutionResult` (lines 241–249) + §5 Stability (line 256: "RFC-0004/0005 pin
  to a `contract_version` major") + `WorkflowRun.contract_version` (line 217).
- **Issue:** `WorkflowRun` carries `contract_version` for downstream stability pinning, but
  `ExecutionResult` — also emitted at run completion and consumed by RFC-0004 — has no
  `contract_version`. The interface surface is inconsistently marked for the stability axis it
  itself mandates.
- **Recommendation:** Add `contract_version: 1.0.0` to `ExecutionResult`, pinned to the same major
  as the producing `WorkflowRun`.

### F-07 — Multiple concurrent runs per Plan not addressed  ·  **Minor**

- **Location:** §6 `start_run(self, plan_ref: str)` (line 273) + §5 `plan_ref` (line 218).
- **Issue:** Nothing forbids two `start_run(P1)` calls producing two active runs of the same Plan.
  Is "one active run per Plan" an invariant, or are parallel runs of one Plan permitted? This
  affects idempotency and intersects the F-03 `pending` edge case.
- **Recommendation:** State the invariant explicitly (recommended: at most one non-terminal run per
  `plan_ref`; a second `start_run` on a Plan with an active run is rejected — or, if parallel runs
  are intended, say so and define how `goal_ref` / `list_runs` disambiguate).
