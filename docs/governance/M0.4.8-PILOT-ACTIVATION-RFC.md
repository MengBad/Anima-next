---

## 1. Objective

Validate the capability routing **governance chain** in a controlled environment:

- capability routing (schema name → `call_capability` → Resolver → Provider)
- allowlist enforcement (fail-closed)
- telemetry (D-A4: `denied / allowed / routed / failed`)
- deny + rollback behavior under real load

**Explicitly NOT a code-execution rollout.** See §7 (F2 Decision Gate).

---

## 2. Scope Boundary

Inherits the M0.4.7 baseline:

- `code.execute` mounted, `capability_only=True`
- `capability_mode` default `False`; `pilot_capability_allowlist` default `[]` (fail-closed)
- registry config-wired (D-A2); replay forced OFF (D-A2)
- dispatch wired via `call()` single entry (D-A3)
- telemetry four-state active (D-A4)

**Included:**

- controlled capability activation (flip `capability_mode` + populate `pilot_capability_allowlist`) via YAML + controlled restart
- governance verification (deny path, schema-gate, audit trail, telemetry counters)

**Excluded:**

- **F2** — actual `code.execute` execution permission
- production rollout (general-user exposure)
- any code change (M0.4.8 is design-only; activation is config-driven)

---

## 3. Cohort Model

Design candidates:

```
pilot cohort
    │
    ├─ identity: explicit principal list in pilot_capability_allowlist
    │            format: "user:<id>" (D-A1 normalized: trim/lower/dedupe, NO wildcard)
    │
    ├─ principal mapping: call-context user_id → "user:<id>" (D-A1 _pilot_principal)
    │
    └─ lifecycle end: remove from allowlist + capability_mode=False + restart
```

**Must answer (open questions for ratification):**

- **How is the cohort defined?** — explicit `user:<id>` list in YAML; size cap TBD (recommend ≤ 3 for infra validation).
- **How is the principal mapped?** — already solved by D-A1: `get_call_context().user_id → user:<id>`; explicit `caller=` override supported.
- **How does the lifecycle end?** — cohort removed from allowlist + `capability_mode=False` + controlled restart; no dangling state (registry rebuilt per restart).

---

## 4. Activation Model

```
OFF (baseline)
  │  config: capability_mode=False, allowlist=[]
  ▼
controlled enable
  │  YAML: capability_mode=True, allowlist=[user:<cohort>]
  │  + controlled restart (config read once at create_default_registry — D-A2)
  ▼
pilot window
  │  observe telemetry + audit; cohort can route governed capabilities
  ▼
rollback  ──────────────┐
  │                    │
  ▼                    │
OFF  ◄─────────────────┘  (any abnormal trigger)
```

**Must include:**

- **kill switch:** set `capability_mode=False` in YAML + restart. No hot-reload (D-A1 R4 / D-A2 R4).
- **restart requirement:** config is read once at registry construction; `_sync_runtime` does not hot-swap capability state.
- **rollback trigger:** any Monitoring stop-criterion (§5) or manual abort.

---

## 5. Monitoring Plan

Reuse D-A4 telemetry counters (no new instrumentation):

```
capability.route.denied    — gate rejections (capability_mode_off / allowlist_empty / no_principal / allowlist_mismatch)
capability.route.allowed   — gate passed
capability.route.routed    — delegated to Resolver-chosen Provider
capability.route.failed    — Provider result judged failure by tool_result_ok()
```

**Normal range (infra-validation Pilot):**

- `denied` ≥ 0 (expected for non-cohort / schema-gated calls)
- `allowed` == cohort's permitted call count
- `routed` == `allowed` (every allowed call routes)
- `failed` == 0 (no execution in scope — see §7; if execution is later permitted, track non-zero)

**Abnormal conditions:**

- `failed` > 0 unexpectedly
- `routed` without corresponding `allowed`
- `denied` spike unrelated to cohort bounds (possible schema-leak or misroute)

**Stop criteria → rollback:** any abnormal condition, or manual abort.

---

## 6. Rollback Procedure

Fastest recovery path:

```
1. capability_mode=False   (edit YAML)
2. restart                 (controlled restart; registry rebuilt with gate OFF)
3. verify metrics          (capability.route.* counters stop incrementing; denied may persist from pre-rollback calls)
```

No data migration, no schema change, no code deploy.

---

## 7. F2 Decision Gate

**F2 = OUT OF SCOPE** until ALL of:

- Pilot data review (telemetry + audit collected during window)
- risk assessment sign-off (see `M0.4.8-RISK-ASSESSMENT.md`)
- new ruling by governance authority

> ⚠️ **Open Design Question (surfaced per Task 3 discipline):** Validating the
> `allowed → routed → executed` happy path inherently executes `code.execute`
> (`code_exec → run_python._invoke`). To validate the chain *without* opening execution
> permission requires either (a) a benign probe capability or (b) a shadow/dry-run mode —
> **both are CODE CHANGES**, which violates the M0.4.8 "no implementation change" rule.
>
> **Resolution:** Pilot validation is scoped to the paths that need NO execution —
> `deny` / `schema-gate` / `audit` / `telemetry(denied)`. The execute-happy-path validation
> is a **DESIGN GATE**: it requires a new scope (Option A — new RFC) before any code change.
> Flagged here; **not implemented** in M0.4.8.
