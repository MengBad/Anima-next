## 1. Objective

> **Pilot A validates governance, NOT execution.**

The validation object is the governance chain — everything up to, and excluding, the provider call:

```
LLM
 ↓
schema exposed?          ← R6 schema gate
 ↓
routing correct?         ← D-A3 single-entry dispatch
 ↓
allowlist checked?       ← D-A1 two-level gate
 ↓
deny / audit correct?    ← capability_route_denied
 ↓
telemetry emitted?       ← D-A4 counters
 ↓
STOP
```

`provider.execute()` is **not** a Pilot A validation object. See §9 (Deferred Validation).

Consequence of this definition — Pilot A requires **none** of:
F2 reopening · sandbox work · `run_python` changes · resource isolation · a new permission model.

## 2. Scope Boundary

Inherits the M0.4.7 baseline (frozen):

- `code.execute` mounted, `capability_only=True`
- `capability_mode` default `False`; `pilot_capability_allowlist` default `[]` (fail-closed)
- registry config-wired (D-A2); replay forced OFF (D-A2)
- dispatch wired via `call()` single entry (D-A3)
- telemetry four-state active (D-A4)

**Included:**

- controlled capability activation (`capability_mode` + `pilot_capability_allowlist`) via YAML + controlled restart
- governance verification: schema exposure, dispatch reach, identity resolution, allowlist fail-closed, telemetry observability

**Excluded:**

- **provider execution** (`code.execute → code_exec → run_python`) — deferred, §9
- **F2** — actual code-execution permission, §7
- production rollout (general-user exposure)
- any code change (M0.4.8 is design-only; activation is config-driven)

## 3. Cohort Model

```
pilot cohort
    │
    ├─ identity: explicit principal list in pilot_capability_allowlist
    │            format: "user:<id>" (D-A1 normalized: trim/lower/dedupe, NO wildcard)
    │
    ├─ principal mapping: call-context user_id → "user:<id>" (D-A1 _pilot_principal)
    │
    └─ lifecycle end: remove from allowlist + capability_mode=False + restart
```

**Open questions resolved for ratification:**

- **How is the cohort defined?** — explicit `user:<id>` list in YAML; recommend size cap **≤ 3** for infra validation.
- **How is the principal mapped?** — solved by D-A1: `get_call_context().user_id → user:<id>`; explicit `caller=` override supported.
- **How does the lifecycle end?** — cohort removed from allowlist + `capability_mode=False` + controlled restart; no dangling state (registry rebuilt per restart).

## 4. Activation Model

```
OFF (baseline)
  │  config: capability_mode=False, allowlist=[]
  ▼
controlled enable
  │  YAML: capability_mode=True, allowlist=[user:<cohort>]
  │  + controlled restart (config read once at create_default_registry — D-A2)
  ▼
pilot window (observation only — no capability invocation, see §6)
  │  observe schema exposure + audit + telemetry
  ▼
rollback  ──────────────┐
  │                    │
  ▼                    │
OFF  ◄─────────────────┘  (any abnormal trigger)
```

- **kill switch:** `capability_mode=False` in YAML + restart. No hot-reload (D-A1 R4 / D-A2 R4).
- **restart requirement:** config is read once at registry construction; `_sync_runtime` does not hot-swap capability state.
- **rollback trigger:** any stop criterion (§5) or manual abort.

## 5. Monitoring Plan

Reuse D-A4 telemetry counters (no new instrumentation):

```
capability.route.denied    — gate rejections (capability_mode_off / allowlist_empty / no_principal / allowlist_mismatch)
capability.route.allowed   — gate passed
capability.route.routed    — delegated to Resolver-chosen Provider
capability.route.failed    — Provider result judged failure by tool_result_ok()
```

**Expected ranges during Pilot A:**

| Counter | Expected | Meaning |
|-|-|-|
| `denied` | ≥ 0, bounded | governance working — non-cohort / gate-closed calls rejected |
| `allowed` | **0** | boundary intact — no invocation crossed the gate |
| `routed` | **0** | boundary intact — no delegation to a Provider |
| `failed` | **0** | no execution in scope |

**Stop criteria → immediate rollback:**

- `allowed > 0` or `routed > 0` — **tripwire**: the execution boundary was approached (see §6)
- `failed > 0` — execution occurred
- `routed` without a matching `allowed` — accounting inconsistency (possible misroute)
- `denied` spike outside cohort bounds — possible schema leak
- manual abort

## 6. Enforcement of the STOP boundary (stated plainly)

The STOP in §1 is a **governance boundary, not a code branch**. At
`anima/tools/__init__.py:326-328`, `allowed` and `routed` are emitted on the line immediately
preceding `await self.call(resolution.provider.tool_name, ...)` — there is **no code-level halt
between `routed` and provider execution**. Introducing one (a shadow / dry-run mode) would be a
code change, which M0.4.8 forbids.

Pilot A therefore enforces STOP with three non-code controls:

1. **Observation-only protocol** — the cohort verifies schema *presence*; it does not invoke the
   governed capability. Positive-path evidence is collected at the schema gate, not by calling.
2. **Tripwire** — `allowed`/`routed` are expected to stay at `0`; any increment is a stop
   criterion (§5) triggering rollback, not a success signal.
3. **Blast-radius cap** — cohort ≤ 3 known principals; `code.execute` already runs on the
   existing hardened `run_python` base, so even an accidental invocation stays inside the
   pre-M0.4.7 sandbox posture (no new exposure is created by this Pilot).

This is sufficient because the positive predicate is provable *without* invocation — see §8 C3.

## 8. Pilot A Success Criteria

Pilot A succeeds when **all five** hold. Each is observable with **zero provider execution**.

| # | Criterion | Observation point | Evidence |
|-|-|-|-|
| C1 | **schema exposure works** | `get_schemas(caller=)` → `capability_schemas(exclude=…)` | cohort session lists `code_execute`; non-cohort session does **not** |
| C2 | **routing reaches capability layer** | `call()` → `call_capability` (`tools/__init__.py:313`) | a non-cohort attempt yields `capability_route_denied` — the deny event itself proves dispatch entered the capability layer |
| C3 | **identity resolution succeeds** | `pilot_capability_permitted(caller)` — the *same* predicate used by both the schema gate and the route gate | positive: cohort sees the schema; negative: reason code distinguishes `no_principal` / `allowlist_mismatch` / `allowlist_empty` |
| C4 | **allowlist behaves fail-closed** | D-A1 two-level gate | empty allowlist ⇒ `allowlist_empty`; unknown principal ⇒ `allowlist_mismatch`; `capability_mode=False` ⇒ `capability_mode_off` — no wildcard, no default-allow |
| C5 | **telemetry is observable** | `MetricsCollector` via WebUI `/api/metrics` | `capability.route.denied` increments with `capability` + `reason` tags; `allowed`/`routed`/`failed` remain `0` |

> **C3 rationale (why the positive path needs no invocation):** `get_schemas` and
> `call_capability` call the *identical* predicate `pilot_capability_permitted(caller)`
> (`tools/__init__.py:290` and `:318`, both dispatching to the definition at `:188`). Proving
> that it resolves a cohort principal to *permitted* at the schema gate proves the same
> resolution at the route gate. One predicate, two observation points — Pilot A uses the
> zero-risk one.

**Explicitly NOT a success criterion:** `python executed`.

## 9. Deferred Validation

```
Deferred Validation

The provider execution path
(code.execute → code_exec → run_python)

is intentionally excluded
from Pilot A.

Validation will occur only
if a future governance decision
opens Pilot B
(F2 reconsideration).
```

Deferred items, carried forward without prejudice:

| Item | Deferred to | Note |
|-|-|-|
| `allowed → routed → executed` happy path | **Pilot B** | requires F2 reconsideration |
| Provider-level failure semantics (`failed` counter under real faults) | Pilot B | `tool_result_ok()` already wired (D-A4); unexercised |
| Sandbox / resource-isolation review for governed execution | Pilot B | out of M0.4.8 entirely |
| Code-enforced shadow / dry-run mode | separate RFC | would be a code change; not needed for Pilot A |

Nothing in this section is a defect of Pilot A. The governance chain is complete and verifiable
on its own; execution is a *downstream* concern behind its own gate.
