## 1. Objective

> **Pilot A validates governance, NOT execution.**

The validation object is the governance chain — everything up to, and excluding, the provider call:

```
LLM
 ↓
schema exposed?          ← R6 schema gate
 ↓
routing correct?         ← D-A3 single-entry dispatch
 ↓
allowlist checked?       ← D-A1 two-level gate
 ↓
deny / audit correct?    ← capability_route_denied
 ↓
telemetry emitted?       ← D-A4 counters
 ↓
STOP
```

`provider.execute()` is **not** a Pilot A validation object. See §9 (Deferred Validation).

Consequence of this definition — Pilot A requires **none** of:
F2 reopening · sandbox work · `run_python` changes · resource isolation · a new permission model.

## 2. Scope Boundary

Inherits the M0.4.7 baseline (frozen):

- `code.execute` mounted, `capability_only=True`
- `capability_mode` default `False`; `pilot_capability_allowlist` default `[]` (fail-closed)
- registry config-wired (D-A2); replay forced OFF (D-A2)
- dispatch wired via `call()` single entry (D-A3)
- telemetry four-state active (D-A4)

**Backward-compatibility & control notes (r3):**

- **Absent config key (F-09):** if `core.config.capability_layer` is absent, `capability_mode`
  defaults to `False` (safe) — no config migration required for legacy deployments.
- **Replay OFF is a separate invariant (F-10):** replay mode forces `capability_mode=False`
  (D-A2); this protects *replay*, not the live pilot. The pilot's backstop is the default-OFF
  gate + detective tripwire + blast-radius cap (§6).
- **Telemetry privacy (F-09):** D-A4 tags are `capability` + `reason` only — no principal id is
  emitted, so metrics observation carries no PII.

**Included:**

- controlled capability activation (`capability_mode` + `pilot_capability_allowlist`) via YAML + controlled restart
- governance verification: schema exposure, dispatch reach, identity resolution, allowlist fail-closed, telemetry observability

**Excluded:**

- **provider execution** (`code.execute → code_exec → run_python`) — deferred, §9
- **F2** — actual code-execution permission, §7
- production rollout (general-user exposure)
- any code change (M0.4.8 is design-only; activation is config-driven)

## 3. Cohort Model

```
pilot cohort
    │
    ├─ identity: explicit principal list in pilot_capability_allowlist
    │            format: "user:<id>" (D-A1 normalized: trim/lower/dedupe, NO wildcard)
    │
    ├─ principal mapping: call-context user_id → "user:<id>" (D-A1 _pilot_principal)
    │
    └─ lifecycle end: remove from allowlist + capability_mode=False + restart
```

**Open questions resolved for ratification:**

- **How is the cohort defined?** — explicit `user:<id>` list in YAML; size cap **≤ 3** for infra validation.
- **How is the principal mapped?** — solved by D-A1: `get_call_context().user_id → user:<id>`; explicit `caller=` override supported.
- **How does the lifecycle end?** — cohort removed from allowlist + `capability_mode=False` + controlled restart; no dangling state (registry rebuilt per restart).

## 4. Activation Model

```
OFF (baseline)
  │  config: capability_mode=False, allowlist=[]
  ▼
controlled enable
  │  YAML: capability_mode=True, allowlist=[user:<cohort>]
  │  + controlled restart (config read once at create_default_registry — D-A2)
  ▼
pilot window (Governance Procedure — "observe only", no capability invocation; see §6.1)
  │  observe schema exposure + audit + telemetry
  ▼
rollback  ──────────────┐
  │                    │
  ▼                    │
OFF  ◄─────────────────┘  (any abnormal trigger)
```

- **kill switch:** `capability_mode=False` in YAML + restart. No hot-reload (D-A1 R4 / D-A2 R4).
- **restart requirement:** config is read once at registry construction; `_sync_runtime` does not hot-swap capability state.
- **rollback trigger:** any stop criterion (§5) or manual abort.
- **Who acts (F-01):** the YAML edit and the restart are performed by an **authorized operator**
  under a signed Approval Record (§12). The Agent does **not** flip the flag autonomously.

## 5. Monitoring Plan

Reuse D-A4 telemetry counters (no new instrumentation):

```
capability.route.denied    — gate rejections (capability_mode_off / allowlist_empty / no_principal / allowlist_mismatch)
capability.route.allowed   — gate passed
capability.route.routed    — delegated to Resolver-chosen Provider
capability.route.failed    — Provider result judged failure by tool_result_ok()
```

**Expected ranges during Pilot A:**

| Counter | Expected | Meaning |
|-|-|-|
| `denied` | ≥ 0, bounded | governance working — non-cohort / gate-closed calls rejected |
| `allowed` | **0** | boundary intact — no invocation crossed the gate |
| `routed` | **0** | boundary intact — no delegation to a Provider |
| `failed` | **0** | no execution in scope |

> **`denied` bound (F-12):** expected volume during the window is low and bounded — routine LLM
> probing of `code_execute` yields a small, steady count. An order-of-magnitude jump (or `denied`
> from a principal outside the named cohort) triggers manual review for possible schema leak.
> No fixed numeric threshold is enforced; anomaly is judged by the reviewer.

> **Metrics access (F-06):** telemetry is observed via the **existing** WebUI `/api/metrics`
> endpoint (D-A4). The reviewer has access to this endpoint in the pilot environment; no new
> surface is opened. Tags are `capability` + `reason` only — **no principal id** is emitted (see
> §2, F-09), so observation carries no PII.

**Stop criteria → immediate rollback:**

> **Control model (F-02):** Two distinct responsibilities.
> **Prevention** = the `capability_mode` gate (`tools/__init__.py:314-315`): when `False`,
> `call_capability` returns *before* any telemetry or provider call — this is the real boundary.
> **Detection** = the telemetry **tripwire** (`allowed`/`routed` > 0): it *detects* a boundary
> crossing *after* it has occurred; it does **not** stop execution. A tripwire firing is a
> rollback trigger, never a success signal.

- `allowed > 0` or `routed > 0` — **tripwire detects** a boundary crossing (see §6); → rollback
- `failed > 0` — execution occurred (detected); → rollback
- `routed` without a matching `allowed` — accounting inconsistency (possible misroute); → rollback
- `denied` spike outside cohort bounds — possible schema leak; → manual review
- manual abort

## 6. Enforcement of the STOP boundary (stated plainly)

The STOP in §1 is a **governance boundary, not a code branch**. At
`anima/tools/__init__.py:326-328`, `allowed` and `routed` are emitted on the line immediately
preceding `await self.call(resolution.provider.tool_name, ...)` — there is **no code-level halt
between `routed` and provider execution**. Introducing one (a shadow / dry-run mode) would be a
code change, which M0.4.8 forbids.

**Two controls, two jobs (F-02):**

- **Prevention — `capability_mode` gate** (`tools/__init__.py:314-315`): when `capability_mode`
  is `False`, `call_capability` returns at the gate *before* emitting any telemetry or calling a
  provider. This is the actual boundary. By default the gate is closed, so the governed route is
  never reached.
- **Detection — telemetry tripwire** (`allowed`/`routed` > 0): a *detective* signal. It fires
  **after** a boundary crossing has already occurred (the provider call is the next line). It
  does **not** prevent execution; it *detects* it so the operator can roll back. A tripwire
  firing is a rollback trigger, never a success signal.

Pilot A holds the boundary with three non-code controls:

1. **Governance Procedure (not technical enforcement)** — the cohort verifies schema *presence*;
   it does **not** invoke the governed capability. "Observe only" is a *procedure* placed on the
   named cohort, not a code-level block. Positive-path evidence is collected at the schema gate,
   not by calling. (F-05 / F-11)
2. **Tripwire (detective)** — `allowed`/`routed` are expected to stay at `0`; any increment is a
   stop criterion (§5) triggering rollback, not a success signal.
3. **Blast-radius cap** — cohort ≤ 3 known principals; `code.execute` already runs on the
   existing hardened `run_python` base, so even an accidental invocation stays inside the
   pre-M0.4.7 sandbox posture (no new exposure is created by this Pilot).

This is sufficient because the positive predicate is provable *without* invocation — see §8 C3.

## 8. Pilot A Success Criteria

Pilot A succeeds when **all five** hold. Each is observable with **zero provider execution**.

| # | Criterion | Observation point | Evidence |
|-|-|-|-|
| C1 | **schema exposure works** | `get_schemas(caller=)` → `capability_schemas(exclude=…)` | **permitted principal** lists `code_execute`; **non-permitted principal** does **not** |
| C2 | **routing reaches capability layer** | `call()` → `call_capability` dispatch (`tools/__init__.py:359`) | a **non-permitted-principal** attempt yields `capability_route_denied` — the deny event itself proves dispatch entered the capability layer |
| C3 | **identity resolution succeeds** | `pilot_capability_permitted(caller)` — the *same* predicate used by both the schema gate and the route gate | positive: cohort sees the schema; negative: reason code distinguishes `no_principal` / `allowlist_mismatch` / `allowlist_empty` |
| C4 | **allowlist behaves fail-closed** | D-A1 two-level gate | **Composition (F-08):** level-1 `capability_mode=False` ⇒ deny (overrides); level-2 allowlist ⇒ deny if empty / unknown / mismatch. Both independently fail-closed — *either* closed ⇒ deny. empty allowlist ⇒ `allowlist_empty`; unknown principal ⇒ `allowlist_mismatch`; `capability_mode=False` ⇒ `capability_mode_off` — no wildcard, no default-allow |
| C5 | **telemetry is observable** | `MetricsCollector` via WebUI `/api/metrics` | `capability.route.denied` increments with `capability` + `reason` tags; `allowed`/`routed`/`failed` remain `0` |

> **C3 rationale (why the positive path needs no invocation):** `get_schemas` and
> `call_capability` call the *identical* predicate `pilot_capability_permitted(caller)`
> (`tools/__init__.py:290` and `:318`, both dispatching to the definition at `:188`). Proving
> that it resolves a cohort principal to *permitted* at the schema gate proves the same
> resolution at the route gate. One predicate, two observation points — Pilot A uses the
> zero-risk one.

**Explicitly NOT a success criterion:** `python executed`.

## 11. Pilot Lifecycle & Completion (F-03 / F-04)

A controlled, time-boxed window with an explicit end-state.

- **Start** — only after Governance Approval (§12) and the controlled restart with
  `capability_mode=True` + `pilot_capability_allowlist=[user:<cohort>]`.
- **Duration** — fixed observation window (recommend ≤ 7 days, or until each of C1–C5 is
  observed ≥ 1×, whichever comes first). Duration is set at Activation (§12.4) and recorded in
  the Approval Record.
- **Success** — all five criteria C1–C5 hold (§8), with `allowed`/`routed`/`failed` = 0
  throughout the window.
- **Close** — deactivation: revert YAML (`capability_mode=False`, empty allowlist) + controlled
  restart; no dangling state (registry rebuilt per restart). Closure declared by the governance
  authority post-review.

**Rollback outcome (F-04):** A tripwire firing + *clean* rollback (service healthy, no state
leak) is a **successful demonstration of the fail-closed controls** — it proves the boundary and
detection work. It is **not** a pilot failure. Only a tripwire with unclean rollback / state leak
/ service outage is a failure. Either way, the pilot returns to OFF and the F2 decision is
unchanged.

## 12. Governance Approval (F-01)

This RFC reaches sign-off only through an explicit governance decision. No code, no activation,
no Pilot execution occurs without it.

### 12.1 Approval Authority
The **governance authority** (the project owner / reviewer) holds sole authority to approve
M0.4.8 Pilot A. Agent implementation may proceed only after this approval.

### 12.2 Approval Preconditions
All of:
- M0.4.7 CLOSED and untouched (verified, `M0.4.8-SCOPE-COMPLIANCE.md`).
- This RFC at status **REVIEW COMPLETE (r3)** with all review findings resolved.
- Risk Assessment (`M0.4.8-RISK-ASSESSMENT.md`) at r3, consistent with this RFC.
- Resolution Checklist (`M0.4.8-REVIEW-RESOLUTION-CHECKLIST.md`) showing 0 Open / blocking items.
- Named cohort principal(s) identified and bounded (≤ 3).

### 12.3 Approval Evidence — the Approval Record
The approval is recorded as an **Approval Record**: a signed entry (this section or a linked
governance note) stating:
- approver identity,
- date,
- approved cohort principal(s),
- approved window duration,
- reference to the Activation Procedure (§12.4).

The Approval Record is the artifact that **authorizes the YAML change**; without it, no restart
occurs. It is stored alongside this RFC under `docs/governance/`.

### 12.4 Activation Procedure (who does what)
| Step | Responsibility | Action |
|-|-|-|
| 1 | Governance authority | Signs the Approval Record (§12.3) |
| 2 | Authorized operator | Edits YAML: `capability_mode: true`, `pilot_capability_allowlist: [user:<cohort>]` |
| 3 | Authorized operator | Performs controlled restart (config read once at `create_default_registry`) |
| 4 | Reviewer | Confirms `denied` telemetry observable; `allowed`/`routed`/`failed` = 0; schema-gate behaviour per C1/C3 |
| 5 | Authorized operator | On any stop criterion, reverts YAML + restart (rollback) |

The YAML flip (step 2) and the restart (step 3) are performed by an **authorized operator** acting
under the Approval Record — **not** by the Agent autonomously.

### 12.5 Rollback Authority
Rollback (revert YAML + controlled restart) may be triggered by:
- the governance authority (at any time), or
- the authorized operator on any stop criterion (§5), or
- an automated health-gate failure post-restart.

The governance authority retains override; the operator is delegated stop-criterion-triggered
rollback.

### 12.6 Completion Criteria
Pilot A is **complete** when: the window elapses (or C1–C5 each observed ≥ 1×) **and** success
holds (§11) **and** the governance authority declares closure. Completion does **not** imply F2;
F2 remains gated by §7.
