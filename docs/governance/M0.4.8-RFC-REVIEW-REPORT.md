## 1. Reviewer's Overall Assessment

The RFC is **fundamentally sound and correctly scoped**. Its core decision — *"Pilot A
validates governance, NOT execution"* — dissolves the previously surfaced design tension at the
root and keeps the Pilot inside the M0.4.7 hardened baseline without code change, sandbox work,
or F2 reconsideration. The cohort model, activation model, monitoring plan, and deferred-validation
section are coherent and internally consistent.

**No blocking issue was found.** All findings below are clarifications, accuracy fixes, or
documentation gaps that can be folded in before or at governance approval. They do not change the
Pilot's safety posture, which genuinely rests on the default-OFF gate (`capability_mode=False` ⇒
`call_capability` returns at `tools/__init__.py:315` before any telemetry or execution).

Findings are enumerated F-01 … F-13. Severity legend: **High / Medium / Low / Info**.

## 2. Findings

### F-01 — Activation authority & sign-off undefined
- **Severity:** Medium
- **Evidence:** §4 "controlled enable … + controlled restart" and §2 "Included: controlled
  capability activation via YAML + controlled restart" describe the *mechanism* but name no
  authority, no sign-off artifact, and no review gate for the actual `capability_mode: true`
  flip. The Scope Compliance report (§3) confirms activation is config-only, but the *decision*
  to flip is itself a governance act on a CLOSED baseline.
- **Impact:** Without a defined approver and approval record, the one irreversible-forward step
  (turning the gate on for a named cohort) could occur outside the governance trail, weakening
  the auditability the whole M0 track is built on.
- **Recommendation:** Add an "Activation Authority & Sign-off" note: the flip requires explicit
  approval by the governance authority (the user), recorded as a signed activation record
  referencing this RFC + a named cohort principal; no restart occurs without it. This is naturally
  resolved *at* the governance-approval step (see §5 recommendation A).

### F-02 — Tripwire is detective, not preventive (accuracy)
- **Severity:** Medium
- **Evidence:** `call_capability` emits `capability.route.allowed` (`:326`) and
  `capability.route.routed` (`:327`), then on the *next line* executes
  `await self.call(resolution.provider.tool_name, ...)` (`:328`). There is **no code-level halt**
  between `routed` and provider execution. §6 and Risk R9 narrative already admit this. Yet §5
  frames `allowed/routed > 0` as a "stop criterion … boundary held," implying prevention.
- **Impact:** A reviewer may believe the tripwire *prevents* execution. It does not — it *detects
  after* the boundary is crossed. The true prevention is the default-OFF gate (`:314-315`).
  Over-reliance on the tripwire overstates the Pilot's safety margin.
- **Recommendation:** Reframe §5/§6: the tripwire is a **detective control** that fires *after*
  the boundary is crossed; prevention rests on the gate (`capability_mode=False` ⇒ deny at `:315`
  before any emission). State plainly: "the tripwire detects a violation; it does not stop one."

### F-03 — No Pilot A closure / duration defined
- **Severity:** Medium
- **Evidence:** §8 gives five pass/fail success criteria but no time-box, no observation-window
  length, and no closure gate. §4 defines rollback but not "what ends the pilot."
- **Impact:** Undefined end-state; a reviewer cannot tell when Pilot A is "done" or who declares
  closure, leaving the pilot open-ended.
- **Recommendation:** Add a short "Pilot Window & Closure" note: fixed window (e.g., N days) or
  until each of C1–C5 is observed ≥1×; deactivation = revert YAML + controlled restart; closure
  declared by the governance authority post-review.

### F-04 — Tripwire-fired-then-rollback outcome undefined
- **Severity:** Low/Medium
- **Evidence:** §5 lists the tripwire as a stop criterion → "immediate rollback," but does not say
  whether a fired tripwire + clean rollback is a *successful* safety demonstration or a *failed*
  pilot.
- **Impact:** This distinction matters for the F2 decision. A clean tripwire+rollback actually
  *proves* the fail-closed design works.
- **Recommendation:** State explicitly: a tripwire firing + clean rollback is a **successful
  demonstration of the fail-closed controls**, not a pilot failure. Only a tripwire with unclean
  rollback / state leak is a failure.

### F-05 — "Observation-only protocol" method unspecified
- **Severity:** Low/Medium
- **Evidence:** §6.1 asserts the cohort verifies schema *presence* without invoking, but gives no
  procedure or endpoint. C1 references "cohort session lists `code_execute`" without stating how
  the reviewer observes it.
- **Impact:** The central evidence-collection method is asserted but not specified; a reviewer
  cannot reproduce or verify it.
- **Recommendation:** Specify the exact read-only observation method — e.g., call
  `get_schemas(caller=cohort_principal)` (or read the LLM-facing schema list for that principal)
  and compare against `get_schemas(caller=non_cohort_principal)`; both are reads, zero invocation.

### F-06 — Metrics accessibility assumption unstated
- **Severity:** Low
- **Evidence:** §5 and §8 C5 rely on WebUI `/api/metrics`; no statement that the reviewer has
  access or that the endpoint is live in the pilot environment.
- **Impact:** If metrics are unreachable, C5 is unobservable and the pilot cannot complete.
- **Recommendation:** State the observability assumption explicitly: reviewer has WebUI metrics
  access; the endpoint is the existing D-A4 one (no new surface, no new tags carrying principal
  identity — see F-09 note on tags).

### F-07 — "cohort session" vs "permitted principal" terminology
- **Severity:** Low
- **Evidence:** §3 uses "principal list"; §8 C1/C2 use "cohort session" / "non-cohort session."
  The capability layer operates on call-context *principal*, not "session."
- **Impact:** Loose terminology could cause misinterpretation of what is actually observed.
- **Recommendation:** Standardize on "permitted principal" (in allowlist) vs "non-permitted
  principal"; drop "session" or define it precisely.

### F-08 — fail-closed composition not stated
- **Severity:** Low
- **Evidence:** §2 says allowlist default `[]` is fail-closed; §8 C4 lists
  `capability_mode=False ⇒ capability_mode_off`. Two independent deny dimensions; the composition
  (level-1 gate = `capability_mode`, level-2 = allowlist) is not stated.
- **Impact:** A reviewer may wonder whether deny requires *both* closed or *either*.
- **Recommendation:** State explicitly: deny if `capability_mode=False` (level-1, overrides) **OR**
  allowlist denies (level-2). Both are independently fail-closed; either closed ⇒ deny.

### F-09 — Absent config-key default unstated (backward compat)
- **Severity:** Low
- **Evidence:** §2/§3 assume `core.config.capability_layer` exists. D-A2 reads it with a `None`
  sentinel → defaults to `capability_mode=False`, so a legacy deployment lacking the key is safe —
  but the RFC does not state this guarantee. (Note: the D-A4 telemetry tags are `capability` +
  `reason` only — **no principal id**, so no PII leak; worth stating for completeness.)
- **Impact:** A legacy deployment without the key could be misread as at risk; the telemetry tag
  set is not documented as privacy-safe.
- **Recommendation:** Add a backward-compatibility line: "if `capability_layer` key is absent,
  `capability_mode` defaults to `False` (safe) — no config migration required." Add that telemetry
  tags carry `capability` + `reason` only, never the principal id.

### F-10 — Replay-OFF is not the pilot's backstop
- **Severity:** Info/Low
- **Evidence:** §2 lists "replay forced OFF (D-A2)" as a baseline guarantee, but the pilot runs on
  the live instance, not replay; replay isolation does not protect the pilot.
- **Impact:** A reader could mistake replay-OFF for the pilot's protection.
- **Recommendation:** Clarify that replay-OFF is a separate baseline invariant; the pilot's
  backstop is the default-OFF gate + detective tripwire + blast-radius cap.

### F-11 — "Observation only" is procedural, not technically enforced
- **Severity:** Low/Medium
- **Evidence:** §4 "pilot window (observation only — no capability invocation)" is a behavioral
  expectation on the human cohort. Technically, if the cohort (or the LLM on its behalf) invokes
  `code_execute` with `capability_mode=True` + in allowlist, it **will** execute. The only
  technical backstop is the detective tripwire + ≤3 blast radius.
- **Impact:** A reader may assume "observation only" is enforced; it is human discipline +
  detective control. Ties directly to F-02.
- **Recommendation:** State plainly that "observation only" is a procedural control on the named
  cohort; the technical guarantee is the default-OFF gate (prevention) + tripwire (detection) +
  blast radius (containment).

### F-12 — "denied ≥ 0, bounded" lacks a quantitative bound
- **Severity:** Low
- **Evidence:** §5 table: `denied` "≥ 0, bounded" with no upper bound or expected rate; the stop
  criterion "denied spike outside cohort bounds" is not quantified.
- **Impact:** Reviewers cannot distinguish normal from anomalous `denied` volume.
- **Recommendation:** Define an expected `denied` range for the window (e.g., "routine LLM probing
  yields ≤ N/day; an order-of-magnitude jump triggers manual review") or state it is observational
  only with manual anomaly review.

### F-13 — C2 code citation imprecision (Info)
- **Severity:** Info
- **Evidence:** §8 C2 cites "call() → call_capability (`tools/__init__.py:313`)". Line 313 is the
  first line *of* `call_capability` (cap_id resolution); the actual `call()`→`call_capability`
  dispatch is at **`:359`** (`return await self.call_capability(name, args, permission_level)`).
- **Impact:** Minor citation imprecision; the asserted fact (dispatch enters the capability layer)
  is correct, only the line reference is off.
- **Recommendation:** Cite `:359` (the dispatch site inside `call()`). Note: C3's `:290` / `:318`
  / `:188` citations were verified accurate.

## 4. Reviewer's Conclusion

The RFC is ready to leave the "Draft" state. The design is correct, the exclusions are clean, and
the safety argument holds (prevention = default-OFF gate; detection = tripwire; containment =
blast radius). The findings are documentation refinements that strengthen clarity and auditability
without altering scope.

task brief and the Resolution Checklist).
