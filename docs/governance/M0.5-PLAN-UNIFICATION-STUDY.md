## 0. Scope and relationship to the Recon

This Study is the second document in the revised M0.5 entry path:

```
Planning Recon Report  →  PLAN-UNIFICATION-STUDY  →  RFC-0002 Draft
```

It exists because the Recon (`M0.5-PLANNING-RECON-REPORT.md`) observed **three independent Plan definitions** already present in the codebase and in the frozen ontology, and concluded that beginning RFC-0002 before reconciling them risks producing a fourth. This Study inventories those three, analyzes their ownership and compatibility, and records the questions that only an RFC (or a Foundation decision) can close.

It does **not** decide which is correct.

Chapters: (1) Inventory, (2) Ownership, (3) Compatibility, (4) Questions.

## Chapter 1 — Inventory

Three Plan definitions are present. Listed without discussion.

### P1 — Constitution `Plan` (code, transient, unwired)

- **Location**: `anima/constitution/state.py:188-205` (dataclass `Plan`).
- **Fields**:
  - `goal_target: str` — the Goal this Plan pursues (content source, read-only)
  - `task_graph: list` — decomposition: list of task descriptors
  - `ordering: list` — sequence / dependencies among Tasks
  - `branching: dict` — conditional / fallback paths (Workflow shape)
  - `rollback: dict` — unwind-on-failure (not a Plan lifecycle)
  - `context_ref: str` — deterministic ref of the Context read (audit only)
  - `emphasis: str` — Drive orientation ("approach" | "avoid"), read-only influence
  - `focus: float` — Drive focus, read-only influence
- **Produced by**: `anima/constitution/planner.py:66` `derive_plan` (returns `Plan(...)`).
- **Consumed by**: nothing in the production runtime. The only in-repo readers are `constitution/execution.py:34` `execute_plan` (a simulated stub that does not dispatch) and `constitution/invariants.py:337` (test wiring). No module outside `anima/constitution/` imports `Plan` (verified by grep: `Plan(` appears only in `constitution/planner.py`, `constitution/invariants.py`, `constitution/state.py`).
- **Persistence**: none. In-memory dataclass, discarded after construction.

### P2 — Production `AgentTask` + `Step` (code, persisted, wired)

- **Location**: `anima/agent/state.py:20-40` (dataclasses `Step`, `AgentTask`).
- **`Step` fields**: `index: int`, `description: str`, `tool_name: str`, `tool_args: dict`, `status: str` (`pending|running|done|failed|skipped`), `result: str`, `error: str`.
- **`AgentTask` fields**: `id: str`, `request: str`, `creator: int`, `status: str` (`planning|executing|completed|failed|cancelled`), `steps: list[Step]`, `current_step: int`, `context: dict`, `error: str`, `created_at: float`, `updated_at: float`.
- **Produced by**: `anima/agent/planner.py:22` `TaskPlanner` (LLM-generated flat `list[Step]`); also `AgentTaskStore.create` (`state.py:95`) which de-duplicates and writes the record.
- **Consumed by**: `anima/agent/executor.py:33` `AgentExecutor` (runs `task.steps`, advances `current_step`, mutates `status`); `anima/core/tasks.py:122` `OwnerTaskAgent` (whole-task ReAct); `anima/tools/builtin/agent_tools.py` (reads/writes tasks); `anima/agent/owner_agent.py` (lifecycle owner).
- **Persistence**: yes. `AgentTaskStore` (`state.py:70-93`) serializes all tasks to `data/agent_tasks.json` via `persistence.write_json`. On restart, any task with `status == "executing"` is re-marked `failed` (`state.py:81-84`) — i.e. the persisted record is authoritative across process restarts.

### P3 — RFC-0106 Ontology `Plan` (frozen document, not code)

- **Location**: `docs/rfc/RFC-0106-Plan.md` — **Anchored / Frozen** (Foundation Validation #6, only modifiable via Foundation Evolution F1–F4).
- **Definition**: `Plan = p(Goal, Drive, Context)` — **Transient-Derived, not Owned** (§4 P1). It is the *graph of Tasks* (RFC-0100 §1.15), not a Goal and not a single Task.
- **Structure dimensions** (§4.1 decomposition schema):
  - **Task graph** — the set of Tasks to perform
  - **Ordering** — sequence / dependencies among Tasks
  - **Branching** — conditional / fallback paths (RFC-0100 §1.16 "Workflow" = runtime form of this)
  - **Rollback** — how to unwind on failure (not a Plan lifecycle)
- **Produced by**: the **Planning Authority** (semantic contract; the same authority that owns Goal per RFC-0105 §6). It is the sole constructor (single-writer rule O1).
- **Consumed by**: the **Execution Authority** (RFC-0107) — Execution *consumes* Plan, never constructs or mutates it (§8, E4).
- **Persistence**: **explicitly forbidden** (P3 / V4): no `Plan.save()`, no `plans.json`, no `PlanMemory`. Only *outcomes* enter Memory (via Reflection), never the Plan itself.
- **Lifecycle**: **none**. Plan exists for the duration of its Goal's pursuit; constructed (not restored) each time, discarded after Execution consumes it (V5).
- **Status / enums**: Plan itself carries no per-step status enum. Execution status is defined separately as `ExecutionStatus` (`constitution/state.py:228-234`: `PENDING|RUNNING|SUCCESS|FAILED|PARTIAL`).

## Chapter 2 — Ownership

For each definition: who **owns** (authority), who **writes** (constructs/mutates), who **reads/consumes**, who **persists**, and who owns any **lifecycle**.

| Aspect | P1 Constitution `Plan` | P2 `AgentTask` + `Step` | P3 RFC-0106 `Plan` |
|--------|------------------------|--------------------------|---------------------|
| **Authority owner** | Planning Authority (per RFC-0106; P1 models P3) | None declared. `AgentTaskStore` owns the persisted record; `TaskPlanner` creates; `AgentExecutor`/`OwnerTaskAgent` drive lifecycle. | Planning Authority (RFC-0106 §6) — sole constructor, single-writer. |
| **Writer (construct)** | `derive_plan` (`constitution/planner.py:66`) | `TaskPlanner.create` (`agent/planner.py`); `AgentTaskStore.create` (`state.py:95`) | Planning Authority (semantic) |
| **Mutator** | none (transient, never mutated) | `AgentExecutor` mutates `step.status`/`result`; `OwnerTaskAgent` mutates `AgentTask.status` (`state.py:24,34`) | none — Execution may only *consume*, not mutate (§8 E4) |
| **Reader / consumer** | **none in production** (only constitution-internal stub `execute_plan`) | `AgentExecutor`, `OwnerTaskAgent`, `agent_tools`, `owner_agent` | Execution Authority (RFC-0107) |
| **Persists?** | **No** — in-memory only | **Yes** — `data/agent_tasks.json` (`AgentTaskStore`) | **No** — explicitly forbidden (P3) |
| **Lifecycle owner** | none (transient) | `AgentTask.status`: `planning|executing|completed|failed|cancelled` (an Owned-style lifecycle) | none (transient, no lifecycle) |
| **Where it lives** | `anima/constitution/` only (zero external imports) | `anima/agent/` + `anima/core/` + `anima/tools/builtin/` (production-wired) | `docs/rfc/RFC-0106-Plan.md` (frozen doc) |

### Observed ownership conflicts (facts, not judgments)

- **Persistence conflict**: P2 persists (`agent_tasks.json`); P3 forbids Plan persistence (P3). Under P3's classification, a persisted Plan store is the mis-classification P1 warns against (§8: "NOT Owned", "no `plans.json` store") and a single-writer (O1) violation (P3/C3).
- **Lifecycle conflict**: P2 carries an Owned-style lifecycle (`planning → executing → completed/failed/cancelled`); P3 asserts Plan has **no** lifecycle (transient, V5).
- **Authority conflict**: P3 assigns construction solely to the Planning Authority; in P2, construction is performed by `TaskPlanner` (a production component) with no declared relationship to the RFC-0106 Planning Authority.
- **Wiring asymmetry**: P1 models P3's shape but is **unwired** (zero production imports) — it cannot currently serve as the runtime Plan. P2 is wired but does not match P3's transient/no-store rule.

## Chapter 3 — Compatibility

Three questions, answered pairwise from observed structure. **No prescription follows.**

### 3.1 P1 ↔ P3 (Constitution `Plan` vs Ontology `Plan`)

- **Compatible?** Structurally: **yes**. P1's fields map onto P3's decomposition schema — `task_graph`↔Task graph, `ordering`↔Ordering, `branching`↔Branching, `rollback`↔Rollback; `goal_target`↔Goal content source; `emphasis`/`focus`/`context_ref`↔Drive orientation + Context read. P1 also matches P3's **transient / no-persistence** rule (in-memory dataclass). Observed: P1 appears to be a code-model of P3.
- **Translatable?** Essentially identity in the transient direction (P1 was written to that schema). No field loss.
- **Must be deprecated?** Not under P3. P1 is a valid code representation of P3's shape. (Whether P1 should be *wired in* is a separate implementation question, not a deprecation.)

### 3.2 P2 ↔ P3 (Production `AgentTask` vs Ontology `Plan`)

- **Compatible?** **Partial overlap, semantic conflict.**
  - Structural overlap: P2 `steps` ≈ P3 Task graph; P2 `Step.index` ≈ P3 Ordering; P2 `Step.status` ≈ P3's separate `ExecutionStatus`.
  - Semantic conflict: P2 **persists** and carries an **Owned-style lifecycle**; P3 forbids both. P2 `Step` also carries `tool_name`/`tool_args`/`result`/`error` — execution binding absent from P3's decomposition schema (P3 is pre-execution structure).
  - Therefore, treating P2 `AgentTask.steps` *as the canonical Plan* contradicts P3's classification (P1/P3: a persisted plan = mis-classification).
- **Translatable?** Partial. `task_graph → steps` and `ordering → index` map; but P2 lacks `branching`/`rollback` fields (present in P1 and P3), so P3's Workflow dimensions are not representable in P2 today.
- **Must be deprecated?** Not decidable in this Study. It depends on the authority choice in Chapter 4 (Q1/Q2): if RFC-0002 adopts P3, then P2's "Plan" aspect (persistence + lifecycle) must be reclassified or relocated; if RFC-0002 adopts P2 as canonical, then P3's transient/no-store rule is overridden for the infra track. Either path is an RFC/Foundation decision, not a finding of this Study.

### 3.3 P1 ↔ P2 (Constitution `Plan` vs Production `AgentTask`)

- **Compatible?** Both represent "steps to do", but at different layers: P1 is transient/abstract (task-graph descriptors, **no** tool binding); P2 is persisted/executable (tool-bound). They are not currently the same object — P1 is unwired, P2 is unaware of P1.
- **Translatable?** Requires mapping `task_graph → steps` and **synthesizing** `tool_name`/`tool_args` (P1 has none). Lossy in the P1→P2 direction (execution binding must be invented); lossy in P2→P1 direction (persistence/lifecycle stripped).
- **Must be deprecated?** Not decidable here. Today neither consumes the other; unification would require either wiring P1 into production (currently zero imports) or remodeling P2 onto P1's schema.

### 3.4 Summary table

| Pair | Structurally compatible | Persists per P3 rule | Carries lifecycle per P3 rule | Translable | Deprecation decidable here? |
|------|------------------------|----------------------|-------------------------------|-----------|------------------------------|
| P1 ↔ P3 | Yes | Yes (both no) | Yes (both no) | Identity | No (already aligned) |
| P2 ↔ P3 | Partial overlap | **No** (P2 persists) | **No** (P2 has lifecycle) | Partial (no branching/rollback in P2) | **No** — needs RFC/Foundation decision |
| P1 ↔ P2 | Different layers | No (P2 persists) | No (P2 has lifecycle) | Lossy both ways | **No** — needs RFC decision |

## Chapter 4 — Questions

Questions that only an RFC (RFC-0002) or a Foundation decision (Foundation Evolution F1–F4) can close. **No answers are given.**

- **Q1 — Authoritative definition.** Which of P1, P2, P3 is the canonical "Plan" for RFC-0002? Or is a fourth representation required? (The Recon's central warning: proceeding without answering this risks a fourth Plan.)

- **Q2 — Authority track collision.** RFC-0002 (000x infra series) and RFC-0106 (010x frozen ontology) both claim the term "Plan" and the "Planning Authority". Does RFC-0002 inherit RFC-0106's Planning Authority, or define a separate infrastructure Planner? This is the cross-track collision the Recon (§11) flagged as the one item that may reshape RFC-0002's boundary.

- **Q3 — Persistence vs transience.** If P3 is authoritative (no Plan persistence), where do in-flight multi-step tasks physically persist across restarts? Is `AgentTaskStore` (`data/agent_tasks.json`) a distinct concept ("execution task record") from "Plan" (transient derivation)? Or is it the same thing under a different name?

- **Q4 — What is `AgentTask.steps`?** Does `AgentTask.steps` represent "Plan", or "Execution Task Record"? If the latter, is its persistence + lifecycle legitimate under that separate name, and does RFC-0002 need to rename/reframe it?

- **Q5 — Workflow shape location.** `branching`/`rollback` exist in P1 and P3 but not in P2. Where do workflow shapes live — in the Plan (P1/P3), or in RFC-0003 Workflow? Is the absence of branching/rollback in P2 a gap RFC-0003 must fill?

- **Q6 — Status / lifecycle enums.** At least six parallel status-string sets were observed in the Recon (constitution `ExecutionStatus`, `AgentTask.status`, `Step.status`, intent statuses, etc.). Should RFC-0002 define a single unified Plan/Step status enum, or keep them separate? If unified, which existing set is the base?

- **Q7 — Memory consumption.** RFC-0004 (Memory) is planned to consume outcomes. Does it consume P3's outcome→Memory path, P2's `AgentTask`→Memory path, or both? Does the choice in Q1/Q3 dictate RFC-0004's input shape?

- **Q8 — Planning Interface output shape.** The Roadmap states RFC-0002 defines the Planning Interface that RFC-0003 consumes. Is that interface's output a single Plan schema distinct from both the ontology (P3) and the execution record (P2)? If so, which of P1/P2/P3 does it extend?

- **Q9 — Wiring cost of unification.** If P1 and P2 are unified, does that require importing `anima.constitution` into the production runtime (currently zero imports of `Plan`)? Is the constitution layer intended to be the runtime Plan, or a validation-only contract?
