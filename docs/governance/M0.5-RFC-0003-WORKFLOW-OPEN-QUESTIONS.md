# M0.5 · RFC-0003 Workflow Recon — WORKFLOW-OPEN-QUESTIONS

> **Recon discipline (per brief).** This document contains **only questions**. None are answered.
> No recommendation, no preferred direction, no RFC-0002 evaluation, no RFC modification.
> These are the unresolved facts surfaced by the inventory/ownership/dependency Recons, handed to
> RFC-0003 (and possibly RFC-0002 follow-up / Foundation Evolution) for resolution.
> Attachment to (not part of) RFC-0003.

---

## Q1 — Is there a canonical "Workflow" state object?

The Recon found **four independent persisted state machines** that each look workflow-like:
`AgentTask`(+`Step`), `WorkflowRun`, `IntentRecord`, `AgendaItem`.
- Do they represent one "Workflow" concept with four facets, or four distinct concerns
  (task execution / content delivery / intent dispatch / autonomous agenda)?
- If one canonical object is expected, which (if any) of the four is it?
- *(Unanswered.)*

## Q2 — Does `Checkpoint` (resume) belong to Workflow?

`Checkpoint` is a Protocol (`contracts/lifecycle.py:36`) with **no reference implementation**;
`ExecutionContextProtocol.checkpoint` allows `None` and the message-pipeline layer is documented
as missing it (`contracts/execution.py:50`). Separately, `AgentTask.current_step` already provides
step-level resume, and `persona_checkpoint.py` exists for an unrelated (persona-drift) domain.
- Is "checkpoint / resume" a Workflow-layer responsibility, an Execution-layer responsibility, or
  neither?
- Should `Checkpoint` be unified with `AgentTask.current_step`, or kept separate?
- *(Unanswered.)*

## Q3 — Does `Retry` belong to Workflow?

Retry is observed in **≥5 independent sites**: `AgentExecutor` (`MAX_TOOL_RETRIES`), LLM handler,
channel (`onebot11`), capability resolver (fallback chain), `IntentLedger.release`→`queued`.
- Is "retry" a Workflow responsibility, or a cross-cutting concern owned by each layer?
- If Workflow owns it, which of the five sites should delegate to it?
- *(Unanswered.)*

## Q4 — Does `Queue` belong to Workflow?

Queues are observed in **≥3 independent sites**: `AgendaQueue`, `IntentLedger`, channel backpressure.
- Is "queue" part of Workflow, or are these independent queues serving different callers?
- Should RFC-0003 define a single queue abstraction, or acknowledge multiple queues?
- *(Unanswered.)*

## Q5 — What is the `AgentTask` / `Step` classification? *(deferred from RFC-0002)*

RFC-0002 explicitly **deferred** the classification of the production `AgentTask`+`Step`
(`agent/state.py:30,19`) — it did not decide whether they are a Plan (RFC-0002), a run-state
(RFC-0003), or both.
- Are `AgentTask`+`Step` the RFC-0003 run-state, the RFC-0002 Plan, or a hybrid?
- If run-state, what is the relationship between `AgentTask.steps` and the RFC-0002 `Plan.task_graph`?
- *(Unanswered; carried over from RFC-0002 §8 / §10 Q6, which deferred it to RFC-0003.)*

## Q6 — Will the constitution `Plan` ever reach production?

Production `AgentExecutor` consumes `AgentTask.steps` (LLM-decomposed). The constitution
`Plan`/`derive_plan`/`execute_plan`/`ExecutionRuntime` are **implemented but unwired** (no
production caller found in this Recon).
- Is the constitution `Plan` path intended to replace `AgentTask.steps` in production, or remain a
  constitution-only (test/isolation) path?
- If it replaces, what migrates `AgentTask.steps` → `Plan.task_graph`?
- *(Unanswered.)*

## Q7 — Does RFC-0003's "Workflow" include the content-delivery ledger?

`WorkflowRun`/`WorkflowStore` (`core/workflows.py`) is a **content-delivery** ledger
(trigger → delivery intent → result), not a task-execution graph. It is wired into
`monitors/scheduler` and `core/autonomy` for automated expressions.
- Does RFC-0003's "Workflow" scope include this delivery ledger, or only task-execution
  orchestration (`AgentTask` world)?
- If included, how is "workflow" reconciled with "delivery ledger"?
- *(Unanswered.)*

## Q8 — Which context object owns mutable lifecycle during a multi-step run?

ADR-0002 splits `PipelineContextProtocol` (Immutable data) from `ExecutionContextProtocol`
(Mutable lifecycle). The production execution path (`AgentExecutor`) uses neither directly — it
mutates `AgentTask`/`Step` in place.
- During a multi-step Agent run, which object is the authoritative mutable lifecycle holder:
  `AgentTask`, `ExecutionContext`, or a new RFC-0003 run-state?
- Is `ExecutionContextProtocol` (currently unwired) the intended ABI for `AgentExecutor`?
- *(Unanswered.)*

## Q9 — Who activates / hands off a run?

RFC-0002 defines **Planning Authority** as the sole activator of a `Plan` (`activate_plan`).
The observed production paths hand off differently:
- `OwnerAgent.submit` → `AgentExecutor.execute` (task run starts immediately, permission-gated).
- `WorkflowRun` moves `triggered → awaiting_delivery` via `bind_intent` (no "activation" authority named).
- Is there one "run activator" authority across task-execution and content-delivery, or are they
  separate (OwnerAgent vs WorkflowStore)?
- *(Unanswered.)*

## Q10 — Are the missing lifecycle primitives Workflow or Execution concerns?

`CancellationToken` / `Deadline` / `Checkpoint` are Protocols with **no reference implementation**
(except `ResourceBudget`). `AgentExecutor` already implements cancel/timeout inline
(`_cancel`, `STEP_TIMEOUT`, circuit-breaker).
- Are these primitives "Workflow" primitives, "Execution" primitives, or shared infrastructure?
- When implemented, should they be injected into `AgentExecutor` / `WorkflowStore` / both?
- *(Unanswered.)*

---

### Notes on these questions (factual, not answers)

- Q1, Q5, Q7, Q9 are about **scope/boundary** of RFC-0003.
- Q2, Q3, Q4, Q10 are about **primitive ownership** (checkpoint / retry / queue / lifecycle).
- Q6, Q8 are about **production wiring** of existing (unwired) contracts.
- Q5 is explicitly **carried over** from RFC-0002 (which deferred it to RFC-0003 per the user's
  ruling on Draft v0.1).
- None of these questions are resolved in this Recon by design.
