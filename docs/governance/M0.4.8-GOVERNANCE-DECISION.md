## 1. Executive Summary

M0.4.7 delivered the two-level capability gate (D-A0 → D-A4) with everything default
OFF, and closed it (commit `4898ead`). M0.4.8 then designed a **controlled Pilot A**
whose sole purpose is to validate the governance chain — schema exposure, routing,
identity resolution, allowlist fail-closed, telemetry — **without executing** the
governed provider (`code.execute → run_python`).

The RFC went through independent review (`c189c10`): 13 findings, all Clarify, zero
Reject, zero Design Defect, zero code-change requirement. All 13 were closed in r3
(`f44ab15`). The RFC now stands at **REVIEW COMPLETE** and is, by the reviewer's own
recommendation, ready for governance approval.

What remains is not an engineering question but a **governance decision**: authorize a
config-only activation (Option A), keep the capability dormant (Option B), or reject
and reopen (Option C). This package exists to put that decision in front of a human
approver with the options, risks, and a blank approval record.

## 2. Decision Required

The approver must choose exactly one:

- **A. Approve Pilot A** exactly as defined in `M0.4.8-PILOT-ACTIVATION-RFC.md` (r3) —
  a config-only activation.
- **B. Keep `capability_mode = OFF` indefinitely** — no Pilot, M0.4.7 stays a dormant
  validated capability.
- **C. Reject Pilot A and reopen the RFC** — send the design back for rework.

This is a governance decision. The Agent does not self-authorize any activation.
(See `M0.4.8-GOVERNANCE-APPROVAL-SUMMARY.md` §12 for the authority model.)

6. Approval Record signed before any config change (see `APPROVAL_RECORD_TEMPLATE.md`).

7. Cohort defined and capped at ≤ 3 principals, named explicitly. ⬜ required at approval.
8. Controlled-restart checklist + post-restart health gate ready. ⬜ required at approval.
9. Telemetry armed: `capability.route.allowed` / `routed` / `failed` expected = 0;

10. Observation-only protocol assigned (named reviewer watching the monitoring window).

Only preconditions 5–10 are open, and they are **activation-time** actions performed by
the human operator under a signed Approval Record — not by the Agent.

## 4. Approval Options (summary; full matrix in `DECISION_MATRIX.md`)

- **Option A — Approve Pilot A (config-only).** Flip `capability_mode = True` for a named
  ≤3-principal cohort via YAML, controlled restart, observe-only window. No code.
  Validates the governance chain on real traffic.
- **Option B — Keep OFF indefinitely.** No activation, no change. M0.4.7 remains a
  validated-but-unexercised dormant capability.
- **Option C — Reject & reopen.** Returns the RFC for rework. Not recommended: review
  found only Clarify issues, no defect.

## 5. Risks (residual, post-r3)

- **R-bound (boundary crossing):** the `routed → execute` transition has no code-level
  halt (`tools/__init__.py:326-328`); the tripwire is **detective**, it fires *after* a
  crossing. True prevention is the `capability_mode` gate (`:314-315`). Mitigation:
  observation-only protocol + ≤3 blast-radius cap on the pre-existing hardened
  `run_python` base (no new exposure).
- **R-ops (operator error):** wrong YAML committed / stale config. Mitigation: pre-restart
  config diff + change-review gate + Approval Record.
- **R-restart:** service fails to come up after restart. Mitigation: staged restart + health
  gate before opening the window; rollback = flip OFF + restart.
- **R-scope:** Pilot scope creep (F2 slips in). Mitigation: explicit out-of-scope list
  (F2 / sandbox / execution / new RFC) baked into the RFC §2 and this package's
  `FINAL_SCOPE_CONFIRMATION.md`.

All residual risks are mitigable with existing M0.4.7 controls. No residual risk requires
new code.

## 6. Recommendation

**Option A**, subject to preconditions 5–10 being satisfied at activation time under a
signed Approval Record.

Rationale: independent review found no blocking issue; the design is intentionally minimal
(config-only, ≤3 cohort, observe-only, fail-closed by construction); and the only residual
risk (boundary crossing) is contained by a detective tripwire + blast-radius cap that, even
if tripped, lands on the pre-existing hardened `run_python` — i.e. creates no new exposure.
Keeping the capability dormant forever (B) leaves the entire M0.4.7 investment unexercised;
reopening (C) would, given the review outcome, most likely reconverge on the same design.

This is a recommendation, not an authorization. The decision is the human approver's.
